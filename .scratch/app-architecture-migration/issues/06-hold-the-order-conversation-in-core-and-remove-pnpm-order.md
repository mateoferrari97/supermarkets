# 06: Hold the order conversation in core and remove pnpm order

**What to build:** The whole conversation of `scripts/order.ts` (postal code first, order text, questions, product selection) is `takeTurn` in `src/core/order-conversation/`, reporting typed progress through `onStep` and stoppable through an `AbortSignal` that reaches every call of both ports. `pnpm order` is removed. See `.scratch/app-architecture-migration/spec.md` (Conversation) and ADR 0008.

**Blocked by:** 01, 05

**Status:** resolved

- [x] `takeTurn(state, replyText, deps, onStep) → { state, reply }`: a new conversation asks "¿A qué código postal es el envío?"; the postal code is parsed with `postalCodeFrom` and checked with `checkDelivery`, refused with today's texts and asked again; once accepted, the next reply is the order text; then the open questions; once nothing is left to ask, the reply is the Product Selection.
- [x] The step event type lives in `core/order-conversation` with typed kinds (understanding the order, searching each Item, translating the preference, Carrefour candidates, simulating the cart, each started and done).
- [x] Every method of `Llm` and `OnlineStore` takes an `AbortSignal`; the Claude Code adapter kills its child process on abort and the Carrefour adapter passes it to `fetch`; both tested.
- [x] `takeTurn` tested with fakes of both ports: postal code missing, rejected, not served and accepted; order with and without questions; unclear answers asked again; product selection reached; `onStep` events in order; an aborted turn leaving the state as before.
- [x] `order:eval` keeps working without `onStep`.
- [x] `scripts/order.ts` and the `order` script removed; `CLAUDE.md` and `ARCHITECTURE.md` updated if 04 is done.
- [x] If a domain term emerges for the conversation, it is added to `GLOSSARY.md`.
- [x] `pnpm check` exits 0.

## Comments

- Layout: `src/core/order-conversation/take-turn.ts` exports `takeTurn(state, replyText, deps, onStep?)`, `NEW_CONVERSATION`, `POSTAL_CODE_QUESTION` and `ORDER_QUESTION`; `src/core/order-conversation/steps.ts` exports the step types (`Step`, `StepEvent`, `OnStep`, `StepOptions`) and `stepsFrom`. The state is `postal-code`, `order` (with the accepted postal code), `questions` (with the `OrderResolution`) or `done` (with the Product Selection). The reply is `ask` (a text), `questions` (the numbered message plus the Items, so the chat can build option chips) or `selection` (the Product Selection plus the Payment Card the Owner named).
- Judgment call on where the `AbortSignal` goes: the ticket fixes `takeTurn(state, replyText, deps, onStep)` and does not name a parameter for the signal, so it is `deps.signal` (optional). The route handler of ticket 07 passes `{ ...deps, signal: request.signal }`.
- Judgment call on "postal code missing": a new conversation is `NEW_CONVERSATION` (`{ stage: "postal-code" }`); an empty reply in that state answers "¿A qué código postal es el envío?", which is how the conversation starts. A reply with no four digits, and one Carrefour rejects (`postal-code-rejected`), both answer `"<reply>" no es un código postal válido. ¿A qué código postal es el envío?`; one Carrefour does not serve answers `Carrefour no entrega en el código postal <code>. ¿A qué código postal es el envío?`. These are the texts of the removed `scripts/order.ts`.
- The question for the order text after the postal code is accepted, "¿Qué necesitás del súper?", is taken from the chat prototype (commit `0cca765`); `scripts/order.ts` took the order text as an argument and had no such question. An empty reply asks it again; an empty answer to the questions repeats them without calling the LLM. A turn after the Product Selection was delivered rejects, since ADR 0008 deletes the session at that point.
- Step kinds: `understand-order` (`Llm.splitOrder`), `understand-answer` (`Llm.mapAnswer`), `search-item` with the phrase (resolving one Item, rewording included), `translate-preference` with the preference, `find-candidates` with the phrase (search and candidate simulations of one Item), `simulate-cart` (the final cart simulation and its replacements). Each is reported `started` and then `done`; a failed or aborted step reports no `done`. `understand-answer` is not in the ticket's list; it was added because answering the questions is an LLM call of several seconds with nothing else to show.
- `resolveOrder`, `answerQuestions` and `pickProducts` take an optional `StepOptions` (`{ signal?, onStep? }`) as their last argument; without it they use a signal that never aborts and report nothing, so `order:eval` and the existing tests call them unchanged.
- Ports: `checkDelivery`, `findCandidates`, `simulate` and every `Llm` method take an `AbortSignal`. `OnlineStore.cartLink` does not: it only builds a URL and makes no call, so there is nothing to stop.
- Claude Code adapter: `ProcessRunner` takes the signal; `createProcessRunner(command)` spawns with Node's `signal` option, which kills the child on abort, and rejects only after the child closes. No session starts when the signal is already aborted. Tested with a fake runner (the signal reaches it; an aborted signal starts nothing) and with real `node` child processes (output and exit code come back; an abort kills a process that never ends and rejects with `AbortError`).
- Carrefour adapter: `HttpRequest` has `signal`, the default client hands it to `fetch`, and every request of `checkDelivery`, `findCandidates` and `simulate` carries it. A failed Tipo lookup is no longer kept in the slug cache (the region cache already dropped failures), so an aborted lookup is asked again next time. Tested with the recorded fixtures and with `fetch` stubbed by `vi.stubGlobal`.
- `takeTurn` tests (`take-turn.test.ts`, fakes of both ports): postal code missing, not parseable, rejected by Carrefour, not served and accepted; empty order text; order with and without questions; unclear answer asked again; empty answer; Product Selection reached from the order and from the answers; a turn after delivery; `onStep` events in order for an order with a preference and for an answer; the signal reaching every port call; an abort in the middle of a turn rejecting with `AbortError` and leaving the state deep-equal to before; an already aborted signal making no call.
- `takeTurn` builds the order resolver on each turn. Measured with the real Catalog Snapshot (37673 grocery products): about 63 ms per build, small next to one Claude Code session, so there is no cache.
- `order:eval` without `onStep`: `pnpm order:eval "un cindor"` ran on 2026-10-14 against real Claude Code sessions with the Catalog Snapshot of the main checkout: `cindor-brand-only: hit`, 2 sessions, 10.9 s, US$ 0.0010. This also ran the new `createProcessRunner` against the real `claude` CLI.
- Removed `scripts/order.ts` and the `order` script. `CLAUDE.md` no longer lists `pnpm order`; `ARCHITECTURE.md` lists `src/core/order-conversation/`, says which port methods take a signal, and describes an order end to end as turns of `takeTurn`. Until ticket 07 builds the chat, no command places an order, as the spec accepts.
- Glossary: no new term. "Conversation", "turn" and "step" are code names for how the chat is held, not words the Owner or the domain uses.
- `pnpm check` exited 0 on 2026-10-14 (19 test files, 207 tests, and the three data validators).
