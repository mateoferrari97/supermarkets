# Architecture

## The product

The Owner writes in one endless Chat ("necesito leche, dos cocas grandes y nada de huevos", "lo mismo que la última vez", "armame una lasaña para 4") and gets a Carrefour cart they only have to open and pay. The Assistant is an agent over that Chat (ADR 0014): it keeps the postal code in the Profile, resolves each Item with tools (a search of the Catalog Snapshot, a second LLM call that keeps the Fits and a pick from checkout simulation in the Branch with the fixed rules of a Selection Policy, ADR 0012), asks its open questions in one round, shows the Order and builds the cart only after the Owner confirms it. The LLM translates; code decides ([LLM](docs/LLM.md)). Terms are defined in [GLOSSARY.md](GLOSSARY.md); the decisions are in [docs/adr/](docs/adr/README.md).

## Layers

The code is one package with the layers of ADR 0006 at the top and features inside the core.

- `src/core/<feature>/`: domain rules, use cases and port types of one feature. It imports only `core` and zod.
  - `src/core/agent-chat/`: the agent chat of ADR 0014: the message of the Chat and its zod schema (`chat.ts`: role `owner` or `assistant`, time, text; `contextMessages` keeps the last 40), the `ChatAgent` port (`agent.ts`: `reply({ messages, profile, order, pastOrders, tools, turnEnded }, signal)` returns the Assistant's text, empty when a tool ended the turn; `turnEnded()` tells the adapter whether a tool really ended it) and the Profile and its schema (`profile.ts`: the postal code), the tools of the agent (`tool.ts`: `AgentTool` with `endsTurn`, `defineTool`, `TurnOutcome`; `tools.ts`: `updateProfile`, which checks the postal code with `OnlineStore.checkDelivery` and saves the Profile only when the Branch delivers, `agentTools`, which builds the tools of a turn, and `renderProfile`; `resolve-item.ts`: `resolveItem`, which reads the Item, runs `matchItems` (search and call 2) and picks with `simulateCart` and the Selection Policy, and when nothing fits returns 3 Alternatives not yet shown (`choose`) or `none`; `choose-alternative.ts`: `chooseAlternative`, which prices the option the Owner chose and replaces the waiting Item; `round.ts`: the round of questions, its zod schema and `renderRound`; `ask-questions.ts`: `askQuestions`, which records one round and ends the turn; `repeat-order.ts`: `repeatOrder`, which opens a new Order from one of the last 3 closed Orders, its products and quantities priced again in today's Branch, with `none` for each one that is no longer available; `reopen-last-order.ts`: `reopenLastOrder`, which reopens the last Order for a Correction (`reopened: true`, which lets `buildCart` skip the wait for the Owner's answer); `propose-order.ts`: `proposeOrder`, which records a proposal and ends the turn; `search-catalog.ts`: `searchCatalog`, the Plan search (scope `plan`, at most 8 queries per call and 3 calls per turn, kept in a `PlanTurn` of `plan-turn.ts`), which adds the products found to the Order's `seen`; `propose-plan.ts`: `proposePlan`, which runs the checks of ADR 0013 (`checkPlan` of `src/core/planning/plan.ts`) over the products seen, merges lines, rounds weights to the Sale Step, prices them from the Catalog Snapshot, sends a Plan over the budget back once per turn, records the Plan as the proposal with its Idea and ends the turn; `build-cart.ts`: `buildCart`, which refuses a proposal that is not the latest or that no Owner message has followed, simulates the whole cart in the Branch, builds the link, closes the Order and ends the turn with the cart), the Order of the Chat (`order.ts`: the zod schemas of `ChatOrder` with its status `draft`, `proposed` or `closed`, its resolved Items by ref (picked, none, or choose with the Alternatives offered and every product shown), the products its Plan searches returned (`seen`), its proposal (a Plan's proposal also carries its Idea and, when still over the budget, `overBudget`) and, once closed, its `Cart` (with the Idea of a Plan), the open Order, `lastClosedOrders` (the last 3 closed Orders), `renderPastOrders`, `renderProposal`, `renderCart` and `renderOrder`; `orders-store.ts`: the `OrdersStore` port of load and save), and `takeAgentTurn` (`take-agent-turn.ts`), which saves the Owner's message, asks the agent with the last 40 messages, the Profile, the open Order, the last 3 closed Orders and the tools (the whole Chat goes to the tools, so `buildCart` can see whether the Owner answered), and saves the reply; when a tool ended the turn, the saved message is the card that tool recorded (its text and parts, such as a proposal or a cart) instead of the agent's text. `agent-chat-fixtures.ts` holds the fakes the tests of the folder share. The agent eval set lives here too: its schema and validator (`eval-set.ts`), `snapshotStore`, an `OnlineStore` that delivers everywhere but where a case says and prices from the Catalog Snapshot (`eval-store.ts`), `runAgentCase`, which plays a case's Owner messages through `takeAgentTurn` over an in-memory Chat, Profile and Orders and records every tool call (`eval-run.ts`), and the scoring of a run by code (`eval-score.ts`).
  - `src/core/order-matching/`: the Item, the grammar of its size and quantity and the rounding of measures (`item.ts`), the catalog product it reads from the Catalog Snapshot (`catalog-product.ts`): sold by weight with its Sale Step or packaged with its size, price, stock, department, Tipo and teasers; the `CatalogSearch` port (`catalog-search.ts`); the `Llm` port (`llm.ts`) with its one task, `fitProducts`; text normalization (`text.ts`); the step events a tool reports while it works (`steps.ts`); and `matchItems` (`match-items.ts`), which searches each Item's Matches and keeps its Fits with `fit-products`, up to 10 calls at a time.
  - `src/core/planning/`: the Plan, its limits and `checkPlan` (`plan.ts`), which checks a Plan against the products seen (ADR 0013) and shows it with snapshot prices and the total.
  - `src/core/product-selection/`: from Fits to a cart; the `OnlineStore` port; postal codes; Selection (`selection.ts`): the size and quantity rule that turns an Item's Fits into Candidates and the Selection Policy that ranks them, with one price per unit of measure and prices from a price source (simulation in the Branch or the Catalog Snapshot); and the simulation of the Candidates and of the whole cart with the Notes of each line (`cart.ts`).
- `src/adapters/<technology>/`: implementations of the ports. They import `core`, `node:*` and zod.
  - `src/adapters/carrefour/`: `OnlineStore` over Carrefour's public API ([Carrefour API](docs/references/carrefour-api.md)).
  - `src/adapters/carrefour/`: also `downloadCatalog` (`catalog-download.ts`), which downloads the whole catalog for `pnpm carrefour:catalog`.
  - `src/adapters/catalog-search/`: `CatalogSearch` in memory over the Catalog Snapshot (`in-memory-catalog-search.ts`, ADR 0012): it leaves out products without stock and the departments Electro y tecnología, Automotor, Indumentaria, Juguetería y Librería and Aire Libre y Ocio, indexes each product's name, brand and Tipo, ranks by BM25 (`bm25.ts`) and by `pg_trgm`-style word similarity (`word-similarity.ts`) for the Item's `product` and, with a brand, also for `product` plus brand, and fuses every ranking by RRF (k = 60), ties in catalog order.
  - `src/adapters/claude-code/`: `Llm` over local Claude Code sessions, and the zod schema that parses their answer. Its `onCall` reports each session with its task, model, the SHA-256 of its system prompt, its input, its raw output, cost and duration.
  - `src/adapters/agent/`: `ChatAgent` over `ToolLoopAgent` from `ai` and the community provider `ai-sdk-provider-claude-code` (`claude-code-agent.ts`). It is the only adapter that imports `ai` and the provider (ESLint allows them only under `src/adapters/agent/`); `src/core/` never imports `ai`. Each turn it reads `prompts/agent/system.md`, appends the `<profile>` and `<order>` blocks to it, builds a small Claude Code session (model `claude-sonnet-5-5` at low effort, no user settings, one in-process MCP server `chat` holding the tools of the turn through `createAiSdkMcpServer`, no built-in tools, no persisted session, at most 10 turns and 0.5 USD) and returns the text; a tool with `endsTurn` aborts the session once it has answered and the turn really ended (a refusal does not end it, so the agent can explain), and the abort the provider throws is read as the end of the turn ([Claude Code provider](docs/references/claude-code-provider.md)).
  - `src/adapters/files/`: every read and write of the data folders (`data-files.ts`), including the Chat (`loadChatMessages` and `appendChatMessage`, validated line by line with the schema of `core`) and the Profile (`loadProfile` and `saveProfile`, validated with `profileSchema`). It is the only place that knows their paths and layout, and the loader of `evals/` data runs the full validation of `core` (schema plus cross-references) and returns the data or the errors.
- `src/compose.ts`: the composition root. It wires adapters into the ports (`createLlm`, `createOnlineStore`, `createCatalogSearch` from the Catalog Snapshot, `createAgentEvaluator({ onCall? })` for `pnpm agent:eval` (it runs a case of the agent eval set over the real agent and `Llm`, the Catalog Snapshot and an in-memory Chat, Profile and Orders, with `snapshotStore` as the `OnlineStore`), `createChatAgent()` and `createAgentTools()` (the tools of a turn over the real `OnlineStore`, the Catalog Snapshot, the `Llm` for call 2 and the Profile and Orders files; it fails with the loader's errors when there is no Catalog Snapshot)), exposes the named loaders and savers of `src/adapters/files/` (`loadChatMessages`, `appendChatMessage`, `loadProfile`, `saveProfile`, `loadOrders`, `saveOrders`, `loadCatalogProducts`, `loadAgentEvalSet`, `saveAgentEvalRun`, ...) and `downloadCatalog(outputDir?)`, and imports only `core` and `adapters`.
- `src/cli/`: one file per operator command, run by `package.json` through `tsx`. A command reads its arguments from `process`, loads and saves only through `compose`, never imports `node:fs` or `adapters`, and reports through `src/cli/report.ts` (print the errors and exit 1, or print the success line).
- `src/app/`: the Owner's chat (ADR 0008, ADR 0014), a Next.js App Router app started with `pnpm dev`. The page `/` (`page.tsx`) loads the whole Chat through `loadChatMessages` on every request and shows the loader's errors when `messages.jsonl` is invalid; `agent-chat.tsx` is its client component; `POST /api/agent` (`api/agent/route.ts`) takes `{ text }`, reads the Chat, the Profile and the Orders from disk, runs `takeAgentTurn` with the open Order, `createChatAgent()` and `createAgentTools()` from `compose`, answers `{ message }` or `{ errors }` (400 invalid body, 409 while a turn runs, 500 invalid Chat, Profile or Orders file, missing Catalog Snapshot or agent failure) and does not stream. A message with a round part is shown as a card (each question with its options and a radio per option, the recommended one marked, a "Más opciones" button per question that has products, "Enviar elegidas" and "Aceptar recomendadas"), interactive while it is the last message of the Chat; each button sends text as the Owner's next message. A message with a proposal part is shown as a card (for a Plan, first its title and the sections of its Idea; then Item asked or, for a Plan, the purpose of the line, product, quantity, price per unit and total, the Notes, what was not found and, when a Plan is still over the budget, by how much), with a "Confirmar" chip while it is the last message of the Chat, which sends "Confirmar" as the Owner's next message; a message with a cart part is shown as a card with the Idea of a Plan above, the lines, the total, the warning and the link to open the cart in Carrefour. The Chat lives only in `.data/chat/`, so a reload or a restart loses nothing. It imports `core` and `compose`, never adapters.
- `scripts/`: repo tooling outside the architecture (`format.mjs`, `no-comments.ts`, `check-docs.ts`).

## Ports and the dependency rule

Four things are ports (ADR 0006, ADR 0012, ADR 0014):

- `ChatAgent` (`src/core/agent-chat/agent.ts`): `reply`, which takes the messages, Profile, Orders and tools of a turn and returns the Assistant's text.
- `Llm` (`src/core/order-matching/llm.ts`): `fitProducts`, which keeps the Fits of one Item among its Matches (call 2 of ADR 0012); the tools call it.
- `OnlineStore` (`src/core/product-selection/online-store.ts`): check delivery to a postal code, simulate a cart, build the cart link.
- `CatalogSearch` (`src/core/order-matching/catalog-search.ts`): `findMatches({ product, brand }, scope, limit)` returns the Matches of one Item, 30 by default, synchronously, among the in-stock products of its scope. Scope `order` leaves out Electro y tecnología, Automotor, Indumentaria, Juguetería y Librería and Aire Libre y Ocio (`EXCLUDED_DEPARTMENTS` in `src/adapters/catalog-search/in-memory-catalog-search.ts`); every order caller, `matchItems` and `pnpm agent:label`, passes it. Scope `plan` searches every in-stock product, those five departments included, whose checkout was verified ([Carrefour API](docs/references/carrefour-api.md#checkout-of-the-departments-orders-leave-out)); only `searchCatalog` passes it. The in-memory adapter builds one index per scope the first time it is searched. It is a port because the search is planned to move to Postgres, not because two adapters exist.

Every method of `ChatAgent`, `Llm` and `OnlineStore` that calls out takes an `AbortSignal`: the Claude Code adapters kill their `claude` process on abort and the Carrefour adapter passes the signal to `fetch`. `cartLink` only builds a URL and takes none.

Static data (Catalog Snapshot, eval set) has no port: it is loaded outside `core` and passed in as arguments. ESLint's `no-restricted-imports` in `eslint.config.js` enforces the rule in `pnpm lint`: `core` imports only `core` and zod; adapters import `core`, `node:*` and zod; `compose` imports `core` and adapters; `cli` and `app` never import adapters, and `cli` never imports `node:fs`. Imports between features inside `core` are free.

## From Fits to a cart

The tools `resolveItem`, `repeatOrder`, `chooseAlternative` and `buildCart` share the core of `src/core/order-matching/` and `src/core/product-selection/`:

1. **Search and call 2.** `matchItems` (`src/core/order-matching/match-items.ts`) runs, per Item, `CatalogSearch.findMatches` in scope `order` for 30 Matches and `Llm.fitProducts` (`fit-products`), up to 10 calls at a time, which keeps the Fits with a Note, or returns a question with up to 5 Alternatives when nothing fits.
2. **Candidates.** `candidatesFor` (`src/core/product-selection/selection.ts`) applies the size and quantity rule to the Fits and keeps up to 10 Candidates per Item, cheapest per unit of measure by snapshot price, each with its code Notes.
3. **Simulation.** `simulateCart` (`src/core/product-selection/cart.ts`) simulates each Candidate of an Item to choose alone at its quantity with `OnlineStore.simulate`, at most 10 at a time, drops the unavailable ones and ranks the rest with the Selection Policy (`rankCandidates` in `selection.ts` with the simulated price source, ADR 0011). An Item with every Candidate unavailable is not got. A quantity promotion hint is added when a simulation at a snapshot teaser's minimum quantity confirms a lower unit price.
4. **Cart.** `buildCart` simulates the whole cart once in the Branch, drops a line that ran out with a Note and builds the link with `OnlineStore.cartLink`; the Cart shown has each line with its product, quantity, prices and Notes, the total and the fixed warning to empty the Carrefour cart first.

## An agent turn end to end

The agent chat (ADR 0014, page `/`) handles one Owner message per turn, and the Chat on disk is the only state.

1. The page sends `POST /api/agent { text }`. The route refuses a second turn while one runs (409), reads the Chat, the Profile and the Orders from `.data/chat/` and fails with the loader's errors when a file is invalid.
2. `takeAgentTurn` saves the Owner's message, builds the tools of the turn (`agentTools`, over the real `OnlineStore`, the Catalog Snapshot and the files) and asks the `ChatAgent` with the last 40 messages, the Profile, the open Order, the last 3 closed Orders and the tools. The adapter renders `prompts/agent/system.md` with the `<profile>`, `<order>` and `<past-orders>` blocks and runs one Claude Code session whose in-process MCP server holds the tools.
3. The agent acts only through the tools. `updateProfile` checks and saves the postal code. `resolveItem` runs `matchItems` (search and call 2) and the Selection Policy over a simulation in the Branch, adds the Item to the open Order (opening one when none is open) and answers `picked`, `choose` or `none`. When it answers `choose` (nothing fits), the Item waits in the Order with the 3 Alternatives, the closest ones of call 2 first and then the best of the Matches, never a product already shown; "más opciones" is the same call with `excludeProductIds`, and it replaces the waiting Item under the same ref. `askQuestions` records every open question of the turn as one round (numbered, with options that are the Alternatives of a ref or free labels, and a recommended one), saves it as the Assistant's message with a `round` part and ends the turn; a second round in the same turn is refused. `proposeOrder` records the proposal, sets the Order `proposed` and ends the turn with the proposal as the Assistant's message, rendered by code.
4. The Owner answers a round in the next message (a tap or their own words) and the agent calls `chooseAlternative` per answer (for "Aceptar las recomendadas", with `recommended` so code reads the option from the latest round in the Chat), which prices the chosen option and turns the waiting Item into a picked one; `proposeOrder` refuses an Item still waiting that it is asked to include (`needs-choice`) and shows a waiting Item it leaves out as a Note. The Owner answers the proposal in the next message ("Confirmar" chip or their own words). The agent calls `buildCart` with the proposal id. Code refuses a proposal that is not the latest, one an Item changed after, and one no Owner message has followed in the Chat. Otherwise it simulates the whole cart in the Branch, drops a line that ran out with a Note, builds the link with `OnlineStore.cartLink`, closes the Order with its cart and ends the turn with the cart as the Assistant's message.
5. A Correction right after the link ("cambiá la leche por descremada") makes the agent call `reopenLastOrder`, `resolveItem` for what is new, `proposeOrder` and `buildCart` in the same turn; the Order the link closed is the one reopened and closed again with a new cart, with no question. Only the last Order reopens, and not while another is open.
6. "Lo mismo que la última vez" makes the agent call `repeatOrder` with the id of that Order from the `<past-orders>` block (the last 3 closed Orders, Items and products bought, no prices): a new Order opens with the same products and quantities priced in today's Branch, each one that is no longer available becomes a not-found Item that the proposal names, and the agent proposes it (with anything new from `resolveItem`). An addition with no open Order ("agregá yogur") makes it ask once, in text, whether to repeat the last Order with it or start a new one.
7. A Plan (recipe, event, weekly menu, gift, advice that ends in a purchase) is built with `searchCatalog` and `proposePlan` instead of `resolveItem` (ADR 0013, ADR 0014). `searchCatalog({ queries })` needs the postal code, searches the Catalog Snapshot in scope `plan` (every in-stock department) for 20 Matches per query, adds the products to the open Order's `seen` (opening an Order when none is open) and answers one row per product (`productId | name | brand | department | type | snapshot price | sale`); it refuses more than 8 queries and a fourth call in the same turn. The `<order>` block lists every product seen, so a revision in a later turn can still use them. `proposePlan({ title, idea, lines, budget?, notes? })` checks, in core, that every product is one of the Order's `seen`, that every quantity is positive and whole (units for a packaged product, grams for one sold by weight), that there are at most 60 lines and that the budget is positive; merges lines with the same product, rounds a by-weight quantity up to its Sale Step with the Note of a Candidate and prices every line and the total from the Catalog Snapshot. A Plan over the budget is refused once per turn (`over-budget`, with the amount to cut), and the revised one is shown with `overBudget`. It records the Plan as the Order's proposal (status `proposed`, the Idea in the proposal) and ends the turn with the card (the Idea, the lines, the total); on a reopened Order it does not end the turn. The Owner revises with a message and the agent calls `proposePlan` again with the whole Plan; when the Owner confirms, `buildCart` runs unchanged on the proposal's lines (a Plan Line counts as the Owner's own choice: no search, no call 2, no Selection Policy), simulates the cart in the Branch and closes the Order with the Idea in the `Cart`. Advice with no purchase is the agent's text with no tool.
8. A tool that ends the turn aborts the session, because the model otherwise writes text that contradicts the card; `takeAgentTurn` saves the card (text and parts) instead of the agent's text. A tool that refuses does not end the turn, so the agent explains.
9. The route answers `{ message }`. The next message about something to buy finds no open Order and opens a new one with its first `resolveItem`.
