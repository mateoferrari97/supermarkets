# Architecture

## The product

The Owner writes a supermarket order in free Spanish ("necesito leche, dos cocas grandes y nada de huevos") and gets a Carrefour cart they only have to open and pay. The Assistant asks for the postal code, reads the order into Items with an LLM, searches the Catalog Snapshot for each Item's Matches, keeps the Fits with a second LLM call, turns them into Candidates with the size and quantity rule, and picks one product per Item from checkout simulation in the Branch with the fixed rules of a Selection Policy (ADR 0012). The LLM translates; code decides ([LLM](docs/LLM.md)). Terms are defined in [GLOSSARY.md](GLOSSARY.md); the decisions are in [docs/adr/](docs/adr/README.md).

## Layers

The code is one package with the layers of ADR 0006 at the top and features inside the core.

- `src/core/<feature>/`: domain rules, use cases and port types of one feature. It imports only `core` and zod.
  - `src/core/agent-chat/`: the agent chat of ADR 0014: the message of the Chat and its zod schema (`chat.ts`: role `owner` or `assistant`, time, text; `contextMessages` keeps the last 40), the `ChatAgent` port (`agent.ts`: `reply({ messages, profile, order, pastOrders, tools, turnEnded }, signal)` returns the Assistant's text, empty when a tool ended the turn; `turnEnded()` tells the adapter whether a tool really ended it) and the Profile and its schema (`profile.ts`: the postal code), the tools of the agent (`tool.ts`: `AgentTool` with `endsTurn`, `defineTool`, `TurnOutcome`; `tools.ts`: `updateProfile`, which checks the postal code with `OnlineStore.checkDelivery` and saves the Profile only when the Branch delivers, `agentTools`, which builds the tools of a turn, and `renderProfile`; `resolve-item.ts`: `resolveItem`, which reads the Item, runs `matchItems` (search and call 2) and picks with `simulateCart` and the Selection Policy, the same path as the order flow, and when nothing fits returns 3 Alternatives not yet shown (`choose`) or `none`; `choose-alternative.ts`: `chooseAlternative`, which prices the option the Owner chose and replaces the waiting Item; `round.ts`: the round of questions, its zod schema and `renderRound`; `ask-questions.ts`: `askQuestions`, which records one round and ends the turn; `repeat-order.ts`: `repeatOrder`, which opens a new Order from one of the last 3 closed Orders, its products and quantities priced again in today's Branch, with `none` for each one that is no longer available; `reopen-last-order.ts`: `reopenLastOrder`, which reopens the last Order for a Correction (`reopened: true`, which lets `buildCart` skip the wait for the Owner's answer); `propose-order.ts`: `proposeOrder`, which records a proposal and ends the turn; `search-catalog.ts`: `searchCatalog`, the Plan search (scope `plan`, at most 8 queries per call and 3 calls per turn, kept in a `PlanTurn` of `plan-turn.ts`), which adds the products found to the Order's `seen`; `propose-plan.ts`: `proposePlan`, which runs the checks of ADR 0013 (`checkPlan` of `src/core/planning/plan.ts`) over the products seen, merges lines, rounds weights to the Sale Step, prices them from the Catalog Snapshot, sends a Plan over the budget back once per turn, records the Plan as the proposal with its Idea and ends the turn; `build-cart.ts`: `buildCart`, which refuses a proposal that is not the latest or that no Owner message has followed, simulates the whole cart in the Branch, builds the link, closes the Order and ends the turn with the cart), the Order of the Chat (`order.ts`: the zod schemas of `ChatOrder` with its status `draft`, `proposed` or `closed`, its resolved Items by ref (picked, none, or choose with the Alternatives offered and every product shown), the products its Plan searches returned (`seen`), its proposal (a Plan's proposal also carries its Idea and, when still over the budget, `overBudget`) and, once closed, its `Cart` (with the Idea of a Plan), the open Order, `lastClosedOrders` (the last 3 closed Orders), `renderPastOrders`, `renderProposal`, `renderCart` and `renderOrder`; `orders-store.ts`: the `OrdersStore` port of load and save), and `takeAgentTurn` (`take-agent-turn.ts`), which saves the Owner's message, asks the agent with the last 40 messages, the Profile, the open Order, the last 3 closed Orders and the tools (the whole Chat goes to the tools, so `buildCart` can see whether the Owner answered), and saves the reply; when a tool ended the turn, the saved message is the card that tool recorded (its text and parts, such as a proposal or a cart) instead of the agent's text. `agent-chat-fixtures.ts` holds the fakes the tests of the folder share.
  - `src/core/conversation-log/`: the events of a Conversation Log and what records them (`conversation-log.ts`): `loggedStore` decorates `OnlineStore`, `loggedSearch` decorates `CatalogSearch`, `loggedSteps` records each step with the duration its done event carries, `loggedTurn` records the Owner's message, the reply and how the turn ended.
  - `src/core/order-matching/`: the order matching flow; the Item, the grammar of its size and quantity and the rounding of measures (`item.ts`), the catalog product it reads from the Catalog Snapshot (`catalog-product.ts`): sold by weight with its Sale Step or packaged with its size, price, stock, department, Tipo and teasers; the `CatalogSearch` port (`catalog-search.ts`); the `Llm` port (`llm.ts`) with its five tasks; text normalization (`text.ts`); and `matchItems` (`match-items.ts`), which searches each Item's Matches and keeps its Fits with `fit-products`, up to 10 calls at a time. Beside them, the eval set (`eval-set.ts`), its scoring (`eval-score.ts`) and the pick on snapshot prices of an eval run (`eval-run.ts`).
  - `src/core/order-conversation/`: the conversation of an order: `takeTurn` (`take-turn.ts`), which sequences the ports; the Order (`order.ts`), pure, which owns the Items of the conversation and every rule about questions, Corrections, the questions message, and the marks and Notes under the table of the Cart shown; and the step events it reports while it works (`steps.ts`).
  - `src/core/planning/`: Plans; the Topic that `route-message` gives the first message of a conversation and the port type of that call (`route-message.ts`); the Plan, the input and output of the `plan` task and `checkedPlan`, which checks an answer and shows its Plan with snapshot prices and the total (`plan.ts`); the search loop of a planning turn (`plan-searches.ts`); the budget retry (`plan-budget.ts`); and the planning eval set (`eval-set.ts`), its scoring (`eval-score.ts`) and the run of a plan case's first message with the `IdeaJudge` port type and the eval run record (`eval-run.ts`).
  - `src/core/product-selection/`: from Fits to a cart; the `OnlineStore` port; postal codes; Selection (`selection.ts`): the size and quantity rule that turns an Item's Fits into Candidates and the Selection Policy that ranks them, with one price per unit of measure and prices from a price source (simulation in the Branch or the Catalog Snapshot); and the simulation of the Candidates and of the whole cart with the Notes of each line (`cart.ts`).
- `src/adapters/<technology>/`: implementations of the ports. They import `core`, `node:*` and zod.
  - `src/adapters/carrefour/`: `OnlineStore` over Carrefour's public API ([Carrefour API](docs/references/carrefour-api.md)).
  - `src/adapters/carrefour/`: also `downloadCatalog` (`catalog-download.ts`), which downloads the whole catalog for `pnpm carrefour:catalog`.
  - `src/adapters/catalog-search/`: `CatalogSearch` in memory over the Catalog Snapshot (`in-memory-catalog-search.ts`, ADR 0012): it leaves out products without stock and the departments Electro y tecnología, Automotor, Indumentaria, Juguetería y Librería and Aire Libre y Ocio, indexes each product's name, brand and Tipo, ranks by BM25 (`bm25.ts`) and by `pg_trgm`-style word similarity (`word-similarity.ts`) for the Item's `product` and, with a brand, also for `product` plus brand, and fuses every ranking by RRF (k = 60), ties in catalog order.
  - `src/adapters/claude-code/`: `Llm` over local Claude Code sessions, the `IdeaJudge` of `pnpm plan:eval` over the same sessions (`createClaudeCodeIdeaJudge`), and the zod schemas that parse their answers. Its `onCall` reports each session with its task, model, the SHA-256 of its system prompt, its input, its raw output, cost and duration.
  - `src/adapters/agent/`: `ChatAgent` over `ToolLoopAgent` from `ai` and the community provider `ai-sdk-provider-claude-code` (`claude-code-agent.ts`). It is the only adapter that imports `ai` and the provider (ESLint allows them only under `src/adapters/agent/`); `src/core/` never imports `ai`. Each turn it reads `prompts/agent/system.md`, appends the `<profile>` and `<order>` blocks to it, builds a small Claude Code session (model `sonnet`, no user settings, one in-process MCP server `chat` holding the tools of the turn through `createAiSdkMcpServer`, no built-in tools, no persisted session, at most 10 turns and 0.5 USD) and returns the text; a tool with `endsTurn` aborts the session once it has answered and the turn really ended (a refusal does not end it, so the agent can explain), and the abort the provider throws is read as the end of the turn ([Claude Code provider](docs/references/claude-code-provider.md)).
  - `src/adapters/files/`: every read and write of the data folders (`data-files.ts`), including the Chat (`loadChatMessages` and `appendChatMessage`, validated line by line with the schema of `core`) and the Profile (`loadProfile` and `saveProfile`, validated with `profileSchema`) and the Conversation Log writer (`openConversationLog`) and the checked-out commit (`headCommit`). It is the only place that knows their paths and layout, and the loader of `evals/` data runs the full validation of `core` (schema plus cross-references) and returns the data or the errors.
- `src/compose.ts`: the composition root. It wires adapters into the ports (`createLlm`, `createOnlineStore`, `createCatalogSearch` from the Catalog Snapshot, `createOrderMatcher({ onCall? })` for `pnpm order:eval`, `createPlanningEvaluator({ onCall? })` for `pnpm plan:eval`, `createChatAgent()` and `createAgentTools()` (the tools of a turn over the real `OnlineStore`, the Catalog Snapshot, the `Llm` for call 2 and the Profile and Orders files; it fails with the loader's errors when there is no Catalog Snapshot) for the agent chat, `createConversationDependencies()` for `takeTurn`, `openConversationLog(sessionId, dependencies)` for the Conversation Log of one chat conversation), exposes the named loaders and savers of `src/adapters/files/` (`loadCatalogProducts`, `loadEvalSet`, `saveEvalRun`, `loadPlanningEvalSet`, `savePlanningEvalRun`, ...) and `downloadCatalog(outputDir?)`, and imports only `core` and `adapters`.
- `src/cli/`: one file per operator command, run by `package.json` through `tsx`. A command reads its arguments from `process`, loads and saves only through `compose`, never imports `node:fs` or `adapters`, and reports through `src/cli/report.ts` (print the errors and exit 1, or print the success line).
- `src/app/`: the Owner's chat (ADR 0008), a Next.js App Router app started with `pnpm dev`. `page.tsx` loads the order data through `compose` and shows the loader's errors instead of the chat when the data is invalid; `chat.tsx` is the client component; `api/turn/route.ts` is the `POST` route handler of one turn; `sessions.ts` is the server-only module that holds the conversations and opens each one's Conversation Log; `turn-events.ts` types the NDJSON events and `step-text.ts` maps step events to them, with a Spanish text when a step starts and its seconds when it is done. It imports `core` and `compose`, never adapters. The agent chat is a second page next to it: `/agent` (`src/app/agent/page.tsx`) loads the whole Chat through `loadChatMessages` on every request and shows the loader's errors when `messages.jsonl` is invalid; `agent-chat.tsx` is its client component; `POST /api/agent` (`src/app/api/agent/route.ts`) takes `{ text }`, reads the Chat, the Profile and the Orders from disk, runs `takeAgentTurn` with the open Order, `createChatAgent()` and `createAgentTools()` from `compose`, answers `{ message }` or `{ errors }` (400 invalid body, 409 while a turn runs, 500 invalid Chat, Profile or Orders file, missing Catalog Snapshot or agent failure) and does not stream. A message with a round part is shown as a card (each question with its options and a radio per option, the recommended one marked, a "Más opciones" button per question that has products, "Enviar elegidas" and "Aceptar recomendadas"), interactive while it is the last message of the Chat; each button sends text as the Owner's next message. A message with a proposal part is shown as a card (for a Plan, first its title and the sections of its Idea; then Item asked or, for a Plan, the purpose of the line, product, quantity, price per unit and total, the Notes, what was not found and, when a Plan is still over the budget, by how much), with a "Confirmar" chip while it is the last message of the Chat, which sends "Confirmar" as the Owner's next message; a message with a cart part is shown as a card with the Idea of a Plan above, the lines, the total, the warning and the link to open the cart in Carrefour. The Chat lives only in `.data/chat/`, so a reload or a restart loses nothing.
- `scripts/`: repo tooling outside the architecture (`format.mjs`, `no-comments.ts`, `check-docs.ts`).

## Ports and the dependency rule

Three things are ports (ADR 0006, ADR 0012):

- `Llm` (`src/core/order-matching/llm.ts`): `routeMessage`, which labels the first message of a conversation with its Topic (`src/core/planning/route-message.ts`), `parseOrder`, which reads an order into the Items of `src/core/order-matching/item.ts`, `fitProducts`, which keeps the Fits of one Item among its Matches, `readReply`, which reads the Owner's reply to questions or a cart into entries per Item with the input types of `src/core/order-matching/read-reply.ts` (ADR 0012), and `plan`, which proposes a Plan from the products a code search returned (`src/core/planning/plan.ts`, ADR 0013); the chat calls all five.
- `OnlineStore` (`src/core/product-selection/online-store.ts`): check delivery to a postal code, simulate a cart, build the cart link.
- `CatalogSearch` (`src/core/order-matching/catalog-search.ts`): `findMatches({ product, brand }, scope, limit)` returns the Matches of one Item, 30 by default, synchronously, among the in-stock products of its scope. Scope `order` leaves out Electro y tecnología, Automotor, Indumentaria, Juguetería y Librería and Aire Libre y Ocio (`EXCLUDED_DEPARTMENTS` in `src/adapters/catalog-search/in-memory-catalog-search.ts`); every order caller, `matchItems` and `pnpm order:label`, passes it. Scope `plan` searches every in-stock product, those five departments included, whose checkout was verified ([Carrefour API](docs/references/carrefour-api.md#checkout-of-the-departments-orders-leave-out)); only `planWithSearches` passes it. The in-memory adapter builds one index per scope the first time it is searched. It is a port because the search is planned to move to Postgres, not because two adapters exist.

Every method of `Llm` and `OnlineStore` that calls out takes an `AbortSignal`: the Claude Code adapter kills its `claude` process on abort and the Carrefour adapter passes the signal to `fetch`. `cartLink` only builds a URL and takes none.

Static data (Catalog Snapshot, eval set) has no port: it is loaded outside `core` and passed in as arguments. ESLint's `no-restricted-imports` in `eslint.config.js` enforces the rule in `pnpm lint`: `core` imports only `core` and zod; adapters import `core`, `node:*` and zod; `compose` imports `core` and adapters; `cli` and `app` never import adapters, and `cli` never imports `node:fs`. Imports between features inside `core` are free.

## An order end to end

An order is a conversation: `takeTurn(state, replyText, deps, onStep)` (`src/core/order-conversation/take-turn.ts`) takes the conversation's state and the Owner's reply and returns the next state and the reply to show. `deps` holds `Llm`, `CatalogSearch`, `OnlineStore` and the turn's `AbortSignal`, which reaches every port call; an aborted turn rejects and the caller keeps the state it had. `onStep` receives each step started and done (`src/core/order-conversation/steps.ts`): understanding the message, understanding the order, understanding the reply, one step per Item while its search and call 2 run, simulating the cart. `takeTurn` creates one `Steps` for the turn and passes it to `matchItems`, so the signal and the step callback travel together; a started event carries a new id and its done event the same id and its duration in milliseconds from an injectable clock, so two steps of the same kind running in parallel each get their own duration and no consumer pairs events itself. The chat in `src/app/` is the only caller that places orders.

The chat runs one turn per `POST /api/turn` (`src/app/api/turn/route.ts`) with the session id and the reply text. A new conversation gets its id from `crypto.randomUUID()` and the first event of its first turn carries it; the browser keeps only that id in React state. The handler claims the session in a `Map` held on `globalThis` (`src/app/sessions.ts`), answers 409 when the session is already working, calls `takeTurn` with `request.signal`, and streams NDJSON events (`src/app/turn-events.ts`): session id, step started, step done with its seconds, questions (the message text and, per open question, the names of its Alternatives, which the chat shows as chips that add the name to the reply), plan (the planner's message and the Plan shown), cart, error. The browser reads them with `fetch` and `response.body.getReader()` (`src/app/chat.tsx`). The conversation stays open after a cart: the chat keeps its input enabled and the session stays. A session is deleted when its turn fails and after one hour without a turn; an aborted turn, such as a closed tab, keeps the state from before the turn. There is no end state: restarting `pnpm dev` or reloading the page starts a new order.

Every conversation is written, as it happens, to its Conversation Log. When `claimSession` creates a session it calls `openConversationLog` (`src/compose.ts`), which opens `.data/conversations/<local start time, YYYY-MM-DD-HHmmss>-<sessionId>.jsonl` through `src/adapters/files/data-files.ts`, writes `conversation-started` with the checked-out commit, and gives the session its own `Llm`, whose `onCall` writes each `llm-call`, its `OnlineStore` wrapped in `loggedStore`, which writes each `store-call` with its input and output, and its `CatalogSearch` wrapped in `loggedSearch`, which writes each `search-call` with the words searched, the limit and the `productId`s found. The route handler runs each turn inside `loggedTurn` and passes `loggedSteps` beside the mapping of step events to the chat's stream, so the log gets `owner-message`, `step-started`, `step-done` with `durationMs`, `assistant-reply` (ask, questions, plan, cart or error) and `turn-ended` with outcome `completed`, `failed` or `aborted` and the error message. Each line is one event with an ISO `at` timestamp and a `type`. A write that fails is printed to the server console and the turn goes on; the log is never shown in the chat.

1. **Data.** Before the first turn, `createConversationDependencies` (`src/compose.ts`), called by `src/app/sessions.ts` when the chat page opens, loads the Catalog Snapshot into the in-memory `CatalogSearch` (`createCatalogSearch`) and stops with every validation error before any order is read.
2. **Postal code.** A new conversation asks "¿A qué código postal es el envío?". `postalCodeFrom` (`src/core/product-selection/postal-code.ts`) reads the code from the Owner's reply; `OnlineStore.checkDelivery` asks Carrefour's regions endpoint (`src/adapters/carrefour/carrefour-store.ts`) whether it delivers there. A refusal asks again; once accepted, the next reply is the first message.
3. **Route and call 1.** `Llm.routeMessage` (`route-message`) labels the first message with its Topic while the chat shows "Entendiendo tu mensaje". An `off-topic` message gets the fixed text "Puedo ayudarte con compras del súper: pedidos, recetas, comidas de la semana, eventos y regalos de Carrefour. ¿Qué necesitás?" and the conversation stays in stage `order`, so the next reply is routed again. A `plan` message starts stage `planning` ([A Plan end to end](#a-plan-end-to-end)). Only replies in stage `order` are routed. An `order` goes on unchanged: `Llm.parseOrder` (`parse-order`) reads the order into Items (`original`, `product`, `brand`, `size`, `quantity`, parsed by `src/core/order-matching/item.ts`) and `ignoredPreference` (ADR 0011).
4. **Search and call 2.** `matchItems` (`src/core/order-matching/match-items.ts`) runs, per Item, `CatalogSearch.findMatches` in scope `order` for 30 Matches and `Llm.fitProducts` (`fit-products`), up to 10 calls at a time, which keeps the Fits with a Note, or returns a question with up to 5 Alternatives when nothing fits. An Item with no Fit is asked (step 5).
5. **Questions.** When any Item has no Fit, the turn's reply is the questions instead of a cart, and the state (stage `questions`) keeps every Item: the ones with Fits with their Candidates, not recomputed, and the asked ones with their question, Alternatives and the questions spent. One numbered message holds one question per asked Item, each Alternative by name and Catalog Snapshot price; nothing is simulated. The Owner's next reply goes to `Llm.readReply` (`read-reply`) with the asked Items and the Items in the cart, numbered (step 9). Per entry: `choice` buys that Alternative as is with the Item's quantity (`candidateOf`), with no search or call 2; `lines` replace the Item by new Items that run step 4; `drop` removes it with the block Note "Saqué: <original>"; `unanswered`, or an asked Item with no entry, is asked again by code with the same text and Alternatives prefixed "Me falta saber de <original>:". An Item is asked at most twice: the first question, an `unanswered` and an answer whose lines have no Fit each spend one, and an Item that would need a third is dropped with a block Note. `newLines` run step 4 as new Items with their own two questions. The turn asks again while any question is open; otherwise it goes on to the cart.
6. **Candidates.** `candidatesFor` (`src/core/product-selection/selection.ts`) applies the size and quantity rule to the Fits and keeps up to 10 Candidates per Item, cheapest per unit of measure by snapshot price, each with its code Notes.
7. **Simulation.** The Order says which Items to buy, each as "choose among these Candidates" or, for an Item already in the cart, "keep this Candidate with this reason" (`ItemToBuy` in `src/core/product-selection/cart.ts`). `simulateCart` simulates each Candidate of an Item to choose alone at its quantity with `OnlineStore.simulate`, at most 10 at a time across the order, drops the unavailable ones and ranks the rest with the Selection Policy (`rankCandidates` in `selection.ts` with the simulated price source, ADR 0011). The eval set's pick calls the same `rankCandidates` with the snapshot price source, so a pass means the chat would pick the same. An Item with every Candidate unavailable is not got. The whole cart is then simulated once; a product unavailable there is replaced by the Item's next ranked Candidate with a Note, until every line is available. A quantity promotion hint is added when a simulation at a snapshot teaser's minimum quantity confirms a lower unit price. The cart returns, per Item, either "bought" with the Candidate it bought and its line (product, quantity, prices, reason and Notes) or "not got" with its Note, plus the total and the cart link. It owns every Note on a line: a kept Item is not simulated alone, gets no promotion hint and comes back with its reason and no Notes, so a Note about an Item already in the cart is not repeated.
8. **Cart.** `OnlineStore.cartLink` builds the link. The Order takes the simulated cart (`takeCart` in `src/core/order-conversation/order.ts`), keeps each bought Candidate as the Item's product in the cart, adds only the marks and the Order-level Notes, and returns the next state and the Cart shown, which is the turn's reply: each line with the Owner's `original`, the product, quantity, prices and its Notes (the call 2 Note first, then code Notes in flow order: size, Sale Step rounding, units of a product sold by weight, substitution, quantity promotion hint); after the table the block (Items not got, those dropped after two questions first, then Items removed, then the ignored card or preference); the total; and, before the link, the fixed warning to empty the Carrefour cart first. The state (stage `cart`) keeps each Item in the cart with the product bought and its quantity.
9. **Corrections.** Every reply after a cart goes to `read-reply` with every Item numbered: Items in the cart with their `original` and the product bought, and asked Items as in step 5. An Item in the cart can get `lines` (a Correction: the new Items run step 4 with two new questions), `drop` (block Note "Saqué: <original>") or, when the reply does not tell which Item it changes, `unanswered` with a question, which spends one of that Item's questions and is asked with no Alternatives; an answer that picks another Item, or none, leaves it in the cart as it was. `newLines` are new Items. Items the reply does not touch go to the cart as kept, with the product bought and its reason (step 7); once no question is open the whole cart is simulated once and the turn replies with a new cart that replaces the previous one. It shows every line; lines added since the last cart are marked `new` ("Nuevo") and corrected ones `changed` ("Cambiado"), by the Order, which tracks whether a cart was shown. A Note shows only in the first cart that holds its Item: a later cart shows the Notes of its marked lines, which the cart simulated again, and of its own block, and the ignored card or preference once.

## A Plan end to end

A message that `route-message` labels `plan` starts a planning conversation instead of an order (ADR 0013). Steps 1 to 3 of an order run first; the stage `planning` then holds the postal code, the planning messages (the Owner's and the planner's, oldest first), every product the searches of this conversation returned, and the last Plan shown. Every reply in stage `planning` goes to the planner; it is not routed again.

1. **Plan call.** `planWithinBudget` (`src/core/planning/plan-budget.ts`) runs `planWithSearches` (`src/core/planning/plan-searches.ts`), which calls `Llm.plan` (`plan`) through `checkedPlan` with the messages, the products seen and the last Plan shown, under the step "Armando el plan". The answer is `{ kind: "search", queries }`, `{ kind: "answer", message, plan | null, budget | null }` or `{ kind: "confirm" }`.
2. **Search rounds.** For a `search`, code runs each query with `CatalogSearch.findMatches({ product: query, brand: null }, "plan", 20)` under one step per round, "Buscando '<query>', ...", adds the products found to the products seen, each once, and calls `plan` again with the queries of this turn and how many products each found (`searches`, rendered as `<searches>`). A turn runs at most 3 rounds; a fourth `search` is not run, and the Owner gets the fixed text `SEARCH_GAVE_UP_TEXT` as an answer with no Plan, so the conversation stays in `planning`. Scope `plan` searches every department, so a gift can be a toy, a book or an appliance; products Carrefour puts in its separate "Hogar y Electro" cart get no warning.
3. **Checks.** `checkPlan` (`src/core/planning/plan.ts`) rejects an answer that breaks a rule, naming the task and the rule: more than 8 queries, more than 60 lines, a product no search of this conversation returned, a quantity that is not positive, not whole units for a packaged product or not whole grams for a by-weight one, a budget that is not positive, a `confirm` when no Plan was shown. It merges lines with the same product into one with the summed quantity and the purposes joined, rounds a by-weight quantity up to its Sale Step with `candidateOf`, so the line gets the same Note a Candidate gets, and computes each line's snapshot price (`snapshotTotal`) and the total.
4. **Budget retry.** When the answer carries the Owner's budget and the Plan's total exceeds it, `planWithinBudget` sends the Plan back to the planner once with the budget and the total, through the same search loop, and shows the revised Plan; if the planner answers with no Plan, the first Plan is shown.
5. **Reply.** An answer with a Plan replies `{ kind: "plan", message, plan, overBudget }`: the chat shows the message, the title, the Idea's sections, a table with each line's product, quantity, purpose and snapshot price, the total, a line saying by how much when the Plan is still over the budget, and a "Confirmar" chip. An answer with no Plan, such as a clarifying question or advice with no purchase ("¿qué vino va con pescado?"), replies with its message as an `ask`. Either way the planner's message joins the planning messages and the conversation stays in `planning`; the last Plan shown is the one with the merged lines and the rounded quantities, and an answer with no Plan keeps the previous one.
6. **Revisions.** The Owner's next message ("que sea para 6") goes to step 1 with the whole planning conversation, the products seen and the last Plan shown, and the planner answers with a revised Plan.
7. **Confirm.** The Owner accepts the last Plan shown in their own words or with the chat's "Confirmar" chip, which sends "Confirmo", and the planner answers `confirm`. `orderFromPlan` (`src/core/order-conversation/order.ts`) turns each Plan Line into an Item whose `original` is "<product name> — <purpose>" and whose only Candidate is `candidateOf(item, product)` at the line's quantity, ready to buy as an `ItemToChoose` with that one Candidate: no search, no `fit-products` and no Selection Policy choice. The Order keeps the Plan's title and Idea (`idea`). Steps 6 to 9 of an order then run unchanged: simulation, the cart with its Notes and lines not got, the link and Corrections. `takeCart` passes the Idea to the Cart shown and keeps it in stage `cart`, so the cart after a Correction shows it too; the chat shows the title and the Idea's sections above the cart table.

## An agent turn end to end

The agent chat (ADR 0014, page `/agent`) handles one Owner message per turn, and the Chat on disk is the only state.

1. The page sends `POST /api/agent { text }`. The route refuses a second turn while one runs (409), reads the Chat, the Profile and the Orders from `.data/chat/` and fails with the loader's errors when a file is invalid.
2. `takeAgentTurn` saves the Owner's message, builds the tools of the turn (`agentTools`, over the real `OnlineStore`, the Catalog Snapshot and the files) and asks the `ChatAgent` with the last 40 messages, the Profile, the open Order, the last 3 closed Orders and the tools. The adapter renders `prompts/agent/system.md` with the `<profile>`, `<order>` and `<past-orders>` blocks and runs one Claude Code session whose in-process MCP server holds the tools.
3. The agent acts only through the tools. `updateProfile` checks and saves the postal code. `resolveItem` runs `matchItems` (search and call 2) and the Selection Policy over a simulation in the Branch, adds the Item to the open Order (opening one when none is open) and answers `picked`, `choose` or `none`. When it answers `choose` (nothing fits), the Item waits in the Order with the 3 Alternatives, the closest ones of call 2 first and then the best of the Matches, never a product already shown; "más opciones" is the same call with `excludeProductIds`, and it replaces the waiting Item under the same ref. `askQuestions` records every open question of the turn as one round (numbered, with options that are the Alternatives of a ref or free labels, and a recommended one), saves it as the Assistant's message with a `round` part and ends the turn; a second round in the same turn is refused. `proposeOrder` records the proposal, sets the Order `proposed` and ends the turn with the proposal as the Assistant's message, rendered by code.
4. The Owner answers a round in the next message (a tap or their own words) and the agent calls `chooseAlternative` per answer (for "Aceptar las recomendadas", with `recommended` so code reads the option from the latest round in the Chat), which prices the chosen option and turns the waiting Item into a picked one; `proposeOrder` refuses an Item still waiting that it is asked to include (`needs-choice`) and shows a waiting Item it leaves out as a Note. The Owner answers the proposal in the next message ("Confirmar" chip or their own words). The agent calls `buildCart` with the proposal id. Code refuses a proposal that is not the latest, one an Item changed after, and one no Owner message has followed in the Chat. Otherwise it simulates the whole cart in the Branch, drops a line that ran out with a Note, builds the link with `OnlineStore.cartLink`, closes the Order with its cart and ends the turn with the cart as the Assistant's message.
5. A Correction right after the link ("cambiá la leche por descremada") makes the agent call `reopenLastOrder`, `resolveItem` for what is new, `proposeOrder` and `buildCart` in the same turn; the Order the link closed is the one reopened and closed again with a new cart, with no question. Only the last Order reopens, and not while another is open.
6. "Lo mismo que la última vez" makes the agent call `repeatOrder` with the id of that Order from the `<past-orders>` block (the last 3 closed Orders, Items and products bought, no prices): a new Order opens with the same products and quantities priced in today's Branch, each one that is no longer available becomes a not-found Item that the proposal names, and the agent proposes it (with anything new from `resolveItem`). An addition with no open Order ("agregá yogur") makes it ask once, in text, whether to repeat the last Order with it or start a new one.
6. A Plan (recipe, event, weekly menu, gift, advice that ends in a purchase) is built with `searchCatalog` and `proposePlan` instead of `resolveItem` (ADR 0013, ADR 0014). `searchCatalog({ queries })` needs the postal code, searches the Catalog Snapshot in scope `plan` (every in-stock department) for 20 Matches per query, adds the products to the open Order's `seen` (opening an Order when none is open) and answers one row per product (`productId | name | brand | department | type | snapshot price | sale`); it refuses more than 8 queries and a fourth call in the same turn. The `<order>` block lists every product seen, so a revision in a later turn can still use them. `proposePlan({ title, idea, lines, budget?, notes? })` checks, in core, that every product is one of the Order's `seen`, that every quantity is positive and whole (units for a packaged product, grams for one sold by weight), that there are at most 60 lines and that the budget is positive; merges lines with the same product, rounds a by-weight quantity up to its Sale Step with the Note of a Candidate and prices every line and the total from the Catalog Snapshot. A Plan over the budget is refused once per turn (`over-budget`, with the amount to cut), and the revised one is shown with `overBudget`. It records the Plan as the Order's proposal (status `proposed`, the Idea in the proposal) and ends the turn with the card (the Idea, the lines, the total); on a reopened Order it does not end the turn. The Owner revises with a message and the agent calls `proposePlan` again with the whole Plan; when the Owner confirms, `buildCart` runs unchanged on the proposal's lines (a Plan Line counts as the Owner's own choice: no search, no call 2, no Selection Policy), simulates the cart in the Branch and closes the Order with the Idea in the `Cart`. Advice with no purchase is the agent's text with no tool.
7. A tool that ends the turn aborts the session, because the model otherwise writes text that contradicts the card; `takeAgentTurn` saves the card (text and parts) instead of the agent's text. A tool that refuses does not end the turn, so the agent explains.
8. The route answers `{ message }`. The next message about something to buy finds no open Order and opens a new one with its first `resolveItem`.
