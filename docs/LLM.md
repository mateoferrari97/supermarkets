# LLM

## The LLM translates, code decides

The LLM turns the Owner's words into tool calls and keeps the Fits of an Item among the Matches code found for it; plain code makes every choice that must be repeatable (ADR 0002, ADR 0011, ADR 0014). The agent reads the Chat and decides what to say and which tool to call. Code searches the Catalog Snapshot for the Matches, checks every number the LLM returns is among them, applies the size and quantity rule, and picks the products from checkout simulation with the fixed rules of the Selection Policy (ADR 0011). Never let the LLM choose a price, compute a quantity or invent a product.

Plans are the one exception ([ADR 0013](adr/0013-in-a-plan-the-llm-proposes-seen-products-and-the-owner-confirms.md)). In a Plan the LLM proposes the products and their quantities, under three rules: every product is one a code search of this Order returned, every quantity is valid for its product (whole units for a packaged product, grams rounded up to its Sale Step for one sold by weight), and code checks both in core. Code still computes every price and total. Nothing reaches the cart until the Owner confirms the Plan, and a confirmed Plan Line counts as the Owner's own choice, so it skips matching and the Selection Policy. Everything else keeps the rule above.

## The ports and their adapters

- `ChatAgent` in `src/core/agent-chat/agent.ts` is the port of the agent; its adapter is `src/adapters/agent/claude-code-agent.ts` ([The agent chat](#the-agent-chat)).
- `Llm` in `src/core/order-matching/llm.ts` is the port of the one task the tools still call, `fitProducts` ([below](#the-fit-products-task)), with the input and output types of the call.
- `src/adapters/claude-code/claude-code-llm.ts` implements `Llm` by running one Claude Code session per call (`claude -p`) with no tools, a JSON schema for the answer and a budget per session set per task in `TASK_BUDGETS_USD` (0.25 USD for `fit-products`; `budgetsUsd` overrides it per task). `TASK_MODELS` fixes the model and effort of each task: `fit-products` runs on `claude-sonnet-5-5` at its default effort (ADR 0012). The model takes no `temperature`, so the same text can resolve differently between runs.
- Every Claude Code session starts with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`: the process runner of `claude-code-llm.ts` (`createProcessRunner`) adds it to the parent's environment, and the agent adapter passes it in the provider's `env`, which the provider merges over its allowlist of the parent's environment. The variable turns off auto-updates, telemetry, error reporting, `/feedback`, release notes, the PR status badge, availability checks, feature-flag fetching and background runs of plugin `command` sources ([Claude Code environment variables](https://code.claude.com/docs/en/env-vars)); these sessions use none of them. It is there for speed: on Claude Code 2.1.302, the start-up a `claude -p` session adds before the model runs was about 1.4 s without it and about 0.28 s with it. Narrower variables (`DISABLE_AUTOUPDATER`, `DISABLE_ERROR_REPORTING`, `DISABLE_GROWTHBOOK`, `DISABLE_TELEMETRY`) did not remove the whole gap. Any value turns it on, `0` and `false` included; the adapters set `1`.
- `src/adapters/claude-code/llm-output-schemas.ts` holds the zod schema the answer is parsed with; an answer that does not fit it fails the call.
- The checks of an answer against its input run in core, not in the adapter (ADR 0006): the adapter keeps the prompt, the output schema and the parsing, and core calls the port through `checkedFitProducts`.
- `src/compose.ts` wires the adapters (`createLlm`, `createChatAgent`); tests use fakes of `Llm` and `ChatAgent` instead.
- The adapter's `onCall` reports every session that returns a result: task, model, effort, SHA-256 of the system prompt, input, raw output, cost and duration. `pnpm agent:eval` sums its cost.

## The `fit-products` task

`fitProducts({ item, alsoInThisLine, matches }, signal)` is call 2 of ADR 0012: one call per Item, which keeps the Item's Fits among its Matches. The adapter sends one `<line>` with `<original>`, `<product>`, `<brand>`, `<also-in-this-line>` (the `product` of the other Items with the same `original`, only when there are any) and `<candidates>`, the Matches numbered from 1 as `number. name | brand | Tipo`.

The LLM returns `{ fits, closest, note, question }`: the numbers of the Matches that fit, a Note for the Owner, and, only when nothing fits, a question with up to 5 `closest` numbers. The schema cannot say how these relate, so core checks the answer against its input in `checkFitProducts` (`src/core/order-matching/match-items.ts`): every number is among the Matches, `question` is set exactly when `fits` is empty, and `closest` has at most 5 numbers and only when `fits` is empty. `matchItems` calls the port only through `checkedFitProducts`, so every adapter and every test fake goes through the same checks. A broken rule throws an error that names the task, the Item and the rule, such as `fit-products answer for Item "una cerveza" breaks a rule: no Alternatives while products fit`, and the tool fails with it.

`matchItems` in `src/core/order-matching/match-items.ts` runs the task for a set of Items, at most 10 calls at a time: for each Item it reports the step "Eligiendo productos para '<original>'" (`src/core/order-matching/steps.ts`), searches 30 Matches with `CatalogSearch`, runs the call, and maps the numbers back to products. It returns per Item its Matches, Fits and Note, or its question with the Alternatives in the order the LLM gave them. One call failing fails the whole set, and no further call starts. `resolveItem` calls it for each Item.

## The agent chat

The agent chat (ADR 0014, the page `/`) is the only way to talk to the Assistant. `ChatAgent` (`src/core/agent-chat/agent.ts`) takes the last 40 messages of the Chat, the Profile, the open Order and the tools of the turn and returns the Assistant's text; its adapter (`src/adapters/agent/claude-code-agent.ts`) runs `ToolLoopAgent` from `ai` over `ai-sdk-provider-claude-code` with the Owner's own Claude Code login. The model is `sonnet`, with `strictMcpConfig`, no setting sources, no built-in tools, no persisted session, `maxTurns` 10 and `maxBudgetUsd` 0.5, which keeps the session small ([Claude Code provider](references/claude-code-provider.md#keeping-the-session-small)). The adapter reads `prompts/agent/system.md` on every turn, appends the `<profile>` block (`renderProfile`: the postal code, or that the Owner has not told it) and the `<order>` block (`renderOrder`: the open Order's status, each resolved Item by ref with its product code, quantity and price, and the latest proposal, or that there is none) and the `<past-orders>` block (`renderPastOrders`: the last 3 closed Orders, oldest first, each with the products bought and their quantities, no prices, or that there are none) and passes the result as the session's system prompt, so a changed Profile or Order reaches the next turn. The tools are core functions (`src/core/agent-chat/tools.ts`) with a zod input; the adapter bridges them into one in-process MCP server named `chat` with `createAiSdkMcpServer` and allows only `mcp__chat__<tool>`, since the provider ignores AI SDK `tools` ([Claude Code provider](references/claude-code-provider.md#tools-reach-the-session-as-an-mcp-server)).

The prompt tells the agent what it can do now (take an order, confirm it and build the cart, and keep the postal code), how to take an order, how to use the Profile, and how to answer. Its first tool is `updateProfile({ postalCode })`: it refuses text that is not four digits (`not-a-postal-code`), asks `OnlineStore.checkDelivery`, refuses a postal code the Online Store does not deliver to (`not-delivered`, the Profile stays as it was) and otherwise saves `{ postalCode }` in `.data/chat/profile.json`, replacing the previous one, and answers `saved`. The prompt tells the agent to call it every time the Owner states a postal code, to report what the tool answered, never to say it saved one the tool did not, and never to ask for a postal code the Profile already holds. Carrefour's regions endpoint accepts any four-digit code that has sellers, so in practice only a malformed code is refused live; the refusal of an unserved code is tested with a fake store.

`resolveItem({ description, brand?, size?, quantity? })` resolves one Item. Size and quantity use the text of the Item line (`common`, `biggest`, `smallest` or `1.5 l`; `minimum`, `3 unit` or `500 g`), parsed by `parseLine` and refused as `invalid-size-or-quantity` when they do not parse. It needs the Profile's postal code and refuses with `no-postal-code` without one. Then it runs `matchItems` (search the Catalog Snapshot and call 2, `fit-products`) and, when something fits, `simulateCart` with the candidates of `candidatesFor`, so the Selection Policy picks after simulation in the Branch with no question. It answers `picked` (a `ref`, the product code, name and brand, the quantity, the price per unit and total, the reason and the Notes), or `none` with a Note when nothing fits or nothing fitting is available. The Item is added to the open Order, which opens with the first `resolveItem` when none is open; an Order that was proposed goes back to `draft`. When nothing fits it answers `choose` or `none` ([below](#rounds-of-questions)).

`proposeOrder({ refs })` takes the refs of the resolved Items to include, records the proposal on the open Order (status `proposed`, id `<order>-<n>`) and ends the turn. The proposal lists each `picked` Item with its product, quantity and price, plus the Note of each `none` Item. The Assistant message that is saved is rendered by code from those results (`renderProposal`, and the proposal part the page shows as a card), not written by the agent, so no product or price in it comes from the model. The adapter aborts the session as soon as a tool with `endsTurn` has answered and the turn really ended (`turnEnded()`; a refusal leaves the session running), because the model otherwise goes on and writes text that contradicts the card ([Claude Code provider](references/claude-code-provider.md#ending-a-turn)). The prompt tells the agent to resolve every Item in one step, to call `proposeOrder` once all are resolved, found or not, to write nothing after it, and never to choose, compare or name a product or a price `resolveItem` did not return. That last rule is held by the prompt for the agent's own text; [the agent eval set](#the-agent-eval-set) scores the products of the cart, not the agent's words.

`buildCart({ proposalId })` builds the cart. It refuses (`refused`, nothing saved, the turn goes on) with `no-postal-code`, `no-open-order` (no Order is open, for instance right after a cart), `no-proposal`, `stale-proposal` (the id is not the latest one, or an Item was resolved after it so the Order went back to `draft`), `unanswered` (the Chat holds no Owner message after the message that showed the proposal; a proposal in the same turn is never answered) or `nothing-available`. Otherwise it simulates every line of the proposal together in the Branch (`OnlineStore.simulate`), drops a line the Branch reports unavailable with the Note `"<product>" no estaba disponible al armar el carrito` and simulates the rest again for the total, builds the link with `OnlineStore.cartLink`, closes the Order with the `Cart` (postal code, lines with the simulated totals, Notes, the warning to empty the Carrefour cart and the link) and ends the turn with the cart as the Assistant message (`renderCart` and a `cart` part the page shows as a card). It does not choose another product for a line that ran out, unlike `simulateCart`, because the ranked Candidates are not kept in the Order. The prompt tells the agent to build the cart only after the Owner clearly accepted the latest proposal, to propose again when the Owner changes something instead, to write nothing after `buildCart` and never to say a cart was built unless it answered `built`.

`reopenLastOrder()` reopens the last Order of the Chat for a Correction: it refuses with `order-open` while any Order is open (the last closed Order is then not the last one) and `no-closed-order` when there is none; otherwise the Order goes back to `proposed` with `reopened: true` and its Items, and `renderOrder` says so. A reopened Order is the one case where `buildCart` does not need an Owner message after the proposal, since the Correction itself is the Owner's answer: `proposeOrder` on a reopened Order records the proposal but does not end the turn, so the agent calls `reopenLastOrder`, `resolveItem` for what is new, `proposeOrder` with the refs the Order should have now and `buildCart` in the same turn, so the Owner gets a new cart (and link) of the same Order with no question; `buildCart` closes the Order again and clears `reopened`. The prompt tells the agent to do this only for a clear Correction of the Order whose link was just given and to ask or start a new Order when unclear. Nothing limits "soon after" in code: whether a message is a Correction is the model's judgement, scored by [the agent eval set](#the-agent-eval-set).

`repeatOrder({ orderId })` repeats a past Order. The agent gets the last 3 closed Orders on every turn (`lastClosedOrders` in `src/core/agent-chat/order.ts`: the closed ones in saved order, the last 3, nothing older and none still open), as Items and products with no prices; what an Order bought is its cart's lines. The tool refuses (`refused`, nothing saved) with `no-postal-code`, `order-open` (an Order is open, so the repeat would mix with it), `unknown-order` (the id is not among those 3) and `nothing-to-repeat`. Otherwise it simulates the cart's products at their quantities together in the Branch (`OnlineStore.simulate`, then again without the ones it reports unavailable, as `buildCart` does), opens a new Order whose Items are those lines priced today (`picked`, reason `Repetido del pedido <id>`) or `none` with the Note `"<product>" ya no está disponible.` for each one the Branch cannot sell now, and answers `repeated` with one `picked` or `none` per Item. It does not search for a replacement of a product that is gone: the Owner sees it in the proposal as not found. The prompt tells the agent to call it for "lo mismo que la última vez" with no open Order, then `resolveItem` for anything new and `proposeOrder` with every ref, and, for an addition with no open Order that is not a Correction ("agregá yogur"), to ask once in one short sentence, naming the products of the last Order, whether to repeat it with the addition or start a new Order, and then to call `repeatOrder` or only `resolveItem` by the answer. Whether the agent asks only then and reads the answer right is scored by [the agent eval set](#the-agent-eval-set).

### Rounds of questions

`resolveItem` answers `choose` when no product fits (call 2 kept none) and there are products to offer: `{ ref, alternatives }` with 3 Alternatives (`productId`, name, brand, snapshot price), the closest ones call 2 named first and then the best remaining Matches, deduplicated. The Item waits in the Order with them and with every product shown so far. "Más opciones" is the same call with `excludeProductIds`: the search leaves those products out (and the ones the waiting Item already showed, even if the agent forgets them), so the next 3 are never a repeat, the waiting Item is replaced under the same ref, and a product that fits among the rest is `picked`. `none` means nothing is left to offer. `askQuestions({ questions })` takes every open question of the turn: the text, optionally the ref of the Item it is about, 1 to 6 options (a `productId` among that ref's Alternatives, or a free `label`) and the position of the recommended one. Code numbers the questions, takes each option's name and price from the Order, saves the round as the Assistant's message (`renderRound` and a `round` part the page shows as a card) and ends the turn; it refuses (`round-already-asked`, `unknown-ref`, `not-an-alternative`, `bad-option`, `bad-recommended`) and then the turn goes on, so every question of a turn ends up in one round. `chooseAlternative({ ref, productId })` records the option the Owner chose (or, with `recommended: true` instead of `productId`, the option the latest round recommended for that ref, which code reads from the Chat so "Aceptar las recomendadas" never depends on the model reading the round right; `no-recommended-product` when that option is not a product): it simulates that product in the Branch at the Item's quantity and replaces the waiting Item with a picked one (`unavailable` when the Branch cannot sell it, `refused` for an unknown ref or an option that was not offered); `proposeOrder` refuses an Item that still waits (`needs-choice`), and the agent leaves out of the proposal an Item the Owner drops; an Item left waiting and left out is shown in the proposal as a Note (`No elegiste una opción para "<description>", así que la dejé afuera.`), so a skipped answer is never silent. The prompt tells the agent to ask only after `choose` or an ambiguous request, once, with every question in one call, to recommend one option per question, to read the Owner's reply (letters, words, a product name or "Aceptar las recomendadas") into `chooseAlternative` calls, and to call `resolveItem` with `excludeProductIds` for more options. The page card sends "Más opciones para la pregunta N", "N: <option name>" lines or "Aceptar las recomendadas" as the Owner's next message. Whether the agent asks only when it should is scored by [the agent eval set](#the-agent-eval-set).

## Prompts

The system prompt of each task is a Markdown file in `prompts/`: `agent/system.md` for the agent chat and `order-matching/fit-products.md` for call 2. The adapter reads the file on each call. Prompts are LLM input, written in English; the Owner's text they receive is Spanish. `pnpm docs:check` does not check them.

## Changing a prompt

1. Edit the prompt. If the answer's shape changes, change the output type in the port and its schema in the adapter together.
2. Run `pnpm agent:eval` (or `pnpm agent:eval <filter>` for the cases whose id or an Owner message contains the filter, and `--runs N` to change the 3 runs per case). It plays each case of [the agent eval set](#the-agent-eval-set) with real Claude Code sessions. It covers `prompts/agent/system.md` and, through `resolveItem`, `prompts/order-matching/fit-products.md`.
3. Read the report: the totals, each failed case with every run's problems and what the agent did in each turn, stale ids, and the sessions, time and cost. Each run is saved in `.data/agent/eval-runs/` with the Catalog Snapshot's date. The command exits 1 when a case not marked `expectedToFail` fails.
4. When a change fixes a case marked `expectedToFail`, the report says so; clear the mark in the eval set.

## Plans in the agent chat

The agent plays the planner of ADR 0013 (ADR 0014). Two tools search and propose, under the checks of the ADR (`checkPlan` in `src/core/planning/plan.ts` is called by the tool):

- `searchCatalog({ queries })` (`src/core/agent-chat/search-catalog.ts`) is the Plan search: scope `plan`, 20 Matches per query, at most 8 queries per call (`PLAN_QUERIES_LIMIT`) and 3 calls per turn (`SEARCH_ROUNDS_LIMIT`; a fourth is refused with `too-many-searches`). It needs the postal code, opens an Order when none is open and saves the products it returns, each once, in the Order's `seen`. It answers one row per product like the `<products>` of the `plan` task (`productId | name | brand | department | type | snapshot price | sale`). The `<order>` block repeats every product seen on later turns, which is what lets a revision ("que sea para 6") use products an earlier turn searched; "products seen" is therefore per Order.
- `proposePlan({ title, idea, lines, budget?, notes? })` (`src/core/agent-chat/propose-plan.ts`) checks the answer in core before anything is shown: every `productId` is among the Order's `seen`; every quantity is positive, whole units for a packaged product and whole grams for a by-weight one; at most 60 lines; a budget, when given, is positive; a product with no snapshot price is refused (`no-price`). A broken rule is `refused` with `breaks-a-rule` and the rule as `detail`, the text `checkPlan` throws, and nothing is saved. Lines of the same product are merged, a by-weight quantity is rounded up to its Sale Step with the Note of a Candidate, and every line and the total are priced from the Catalog Snapshot: the model never states a price. A Plan whose total exceeds the budget is refused once per turn with `over-budget` and the amount to cut, so the agent revises it (the equivalent of the budget retry); the revised Plan, or a second over-budget Plan in the same turn, is shown with `overBudget`, the amount over. The accepted Plan is the Order's proposal, with its Idea, and the turn ends with its card rendered by code. `notes` carries what the Owner should know that the card does not show (an ingredient no search found).

The prompt (`prompts/agent/system.md`, section "Plans") carries what `prompts/planning/plan.md` taught the planner: what a Plan is for, search in catalog words and not more than 8 queries, only `productId`s that `searchCatalog` returned, whole units and whole grams, one line per product with a purpose and a reason, what the Idea holds for a recipe, an event, a weekly menu, a gift and advice, diets and allergies in every line, what the Owner already has, the budget, revisions with the whole Plan, and advice answered in text with no search. A confirmed Plan goes through `buildCart` unchanged: a Plan Line counts as the Owner's own choice, so there is no `resolveItem` for it, and `buildCart` closes the Order with the Idea in the `Cart`. Whether the model keeps these rules is scored by [the agent eval set](#the-agent-eval-set) over its tool calls and carts,.

## The agent eval set

`evals/agent.json` measures what the agent does over a Chat, not how a task reads a text. A case plays scripted Owner messages, one turn each, through `takeAgentTurn` with the real agent (`createChatAgent`) and the real `Llm` for call 2, over an in-memory Chat, Profile and Orders (`runAgentCase` in `src/core/agent-chat/eval-run.ts`), so `.data/chat/` is never touched. The `OnlineStore` is `snapshotStore` (`eval-store.ts`): it delivers to any postal code except the ones a case lists in `doesNotDeliver`, simulates each product at its Catalog Snapshot price and in stock, and builds a link under `https://eval.invalid/cart`, so no run calls Carrefour and Branch stock and promotions do not change a result. The Catalog Snapshot is not pinned: each run uses the current one and records its date. Every tool call of a turn is recorded with its input and output.

A case has an `id`, the user stories of the spec it `covers`, an optional `expectedToFail` with the reason, and:

- `setup`: the `postalCode` of the Profile (`null` for none), optionally `doesNotDeliver`, an earlier `chat` (messages with a role and a text) and `pastOrders` (closed Orders as `productId` and `quantity` lines, bought at the snapshot price, so the agent receives them as `<past-orders>`).
- `turns`: for each Owner message, `ends` (`text`, `round`, `proposal` or `cart`: the kind of message the Assistant saved), optionally `calls` (tools the turn must call), `noCalls` (tools it must not call), `minQuestions` (questions the round has) and `moreOptions` (a `resolveItem` call with `excludeProductIds`).
- Optionally `postalCode`, the Profile at the end, and `cart`: `null` for no cart, or the cart the last turn must end with, as `lines` (each a `product` that names it for people and is never compared, the `fits` productIds of which one must be in the cart and optionally a `quantity`), `exact` (default true: no line beyond `lines`) and `minLines`, for a Plan, whose products the agent picks.

Besides the expectations of the case, code applies to every turn the rules of the spec: the agent does not ask for the postal code when the Profile has it (a question with the word "postal" in the reply); it asks a round with `askQuestions` only when a `resolveItem` of the same turn answered `choose`; it calls `buildCart` only after the Owner was shown a proposal, or in the turn that reopens the last Order; and no `buildCart` the tool refused (a refusal means the agent called it too early). A refused `proposeOrder` is not counted, since the agent goes on and proposes again. A refused `askQuestions` is not counted as a round either, and a turn that refuses a postal code may ask for another one. A case passes when every run gives no error and no problem.

The cases cover the user stories that are the agent's behaviour: the postal code asked once and kept (`postal-code-once`), changed or refused when no Branch delivers (`change-postal-code`), "agregá yogur" after a past Order asked in text (`add-to-past-order`), "lo mismo que la última vez" (`repeat-order`), precise products with no question (`precise-product`), 3 options and "más opciones" (`more-options`), one round for all open questions answered with "Aceptar las recomendadas" (`one-round`), the Order shown before any cart (`confirm-first`), a Correction after the link (`correction`), a recipe or a gift as a Plan and advice with no purchase (`plan`) and a question that is not about shopping (`off-topic`). The stories about the page (the Chat open on load, the cards) and about the code (the Chat as the only state, tools tested with fakes, the agent behind a port) are not agent behaviour and are tested in `docs/TESTING.md`. `pnpm agent:eval-set` validates the set with zod (unique ids, every story covered, no turn that requires and forbids the same tool, questions only in a turn that ends with a round, a cart expectation only when the last turn ends with a cart, an expected postal code only when a turn can call `updateProfile`, past Orders only with a postal code) and runs in `pnpm check`; it never reads the Catalog Snapshot.

`pnpm agent:eval [filter...] [--runs N]` runs the cases whose id or an Owner message contains a filter, 3 times each by default, with real Claude Code sessions, and prints each failed run as it ends. The report gives the cases passed, the errors, stale `productId`s (missing or out of stock in the current Catalog Snapshot), time and cost per case and, for each failed case, every run's problems and what the agent did in each turn (tools and how it ended). It saves the run in `.data/agent/eval-runs/` and exits 1 when a case not marked `expectedToFail` fails. The cost is that of the sessions of call 2; the agent's own sessions run through the AI SDK and are not costed. It does not run in `pnpm check`, because it makes live calls and costs money. Labelling a case by hand: `pnpm agent:label <words> [--brand <brand>]` lists the top 50 products of the Catalog Snapshot for a phrase with `productId`, name, brand, size, price and stock.
