# LLM

## The LLM translates, code decides

The LLM turns the Owner's words into fixed forms; plain code makes every choice that must be repeatable (ADR 0002, ADR 0011). It reads an order into Items, keeps the Fits of an Item among the Matches code found for it, and reads the Owner's reply to questions or a cart (ADR 0012). Code searches the Catalog Snapshot for the Matches, checks every number the LLM returns is among them, applies the size and quantity rule, and picks the products from checkout simulation with the fixed rules of the Selection Policy (ADR 0011). Never let the LLM choose a price, compute a quantity or invent a product.

Plans are the one exception ([ADR 0013](adr/0013-in-a-plan-the-llm-proposes-seen-products-and-the-owner-confirms.md)). In a Plan the LLM proposes the products and their quantities, under three rules: every product is one a code search of this conversation returned, every quantity is valid for its product (whole units for a packaged product, grams rounded up to its Sale Step for one sold by weight), and code checks both in core. Code still computes every price and total. Nothing reaches the cart until the Owner confirms the Plan, and a confirmed Plan Line counts as the Owner's own choice, so it skips matching and the Selection Policy. Orders keep the rule above.

## The port and its adapter

- `Llm` in `src/core/order-matching/llm.ts` is the port: one method per task (`routeMessage`, `parseOrder`, `fitProducts`, `readReply`, `plan`) with the input and output types of each call.
- `src/adapters/claude-code/claude-code-llm.ts` implements it by running one Claude Code session per call (`claude -p`) with no tools, a JSON schema for the answer and a budget per session set per task in `TASK_BUDGETS_USD` (1 USD for `plan`, which reads many products, and 0.25 USD for every other task; `budgetsUsd` overrides it per task). `TASK_MODELS` fixes the model and effort of each task: `route-message` runs on `claude-haiku-5-5` at its default effort, `parse-order` and `read-reply` run on `claude-sonnet-5-5` with `--effort low` and `fit-products` and `plan` on `claude-sonnet-5-5` at their default effort (ADR 0012). The model takes no `temperature`, so the same text can resolve differently between runs.
- `src/adapters/claude-code/llm-output-schemas.ts` holds the zod schemas the answers are parsed with; an answer that does not fit its schema fails the call; the `size` and `quantity` of a line are built from the patterns and parsers of `src/core/order-matching/item.ts`, so the JSON schema sent to Claude Code carries the same patterns the parser reads.
- The checks of an answer against its input, for `fit-products`, `read-reply` and `plan`, run in core, not in the adapter (ADR 0006): the adapter keeps the prompts, the output schemas and the parsing of lines, and core calls the port through `checkedFitProducts`, `checkedReadReply` and `checkedPlan`.
- `src/compose.ts` wires the adapter (`createLlm`); tests use fakes of `Llm` instead.
- The adapter's `onCall` reports every session that returns a result: task, model, effort, SHA-256 of the system prompt, input, raw output, cost and duration. `pnpm order:eval` sums its cost; the chat writes it to the Conversation Log in `.data/conversations/` (see [ARCHITECTURE](../ARCHITECTURE.md#an-order-end-to-end)).

## The `route-message` task

`routeMessage(text, signal)` labels the first message after the postal code with its Topic, before anything else reads it. The adapter sends the Owner's text wrapped in `<message>` tags. The LLM returns `{ topic }`, one of `order`, `plan` or `off-topic` (`src/core/planning/route-message.ts`); any other value fails the schema. `takeTurn` calls it only in stage `order`, under the step "Entendiendo tu mensaje". An `order` goes to `parse-order` with the same text; `plan` starts stage `planning` and goes to the [`plan` task](#the-plan-task) with the same text; `off-topic` gets the fixed text "Puedo ayudarte con compras del súper: pedidos, recetas, comidas de la semana, eventos y regalos de Carrefour. ¿Qué necesitás?" and the conversation stays in stage `order`. The prompt prefers `order` when in doubt, so a plain order never lands in planning. Like every call, it is reported by `onCall` and written to the Conversation Log.

## The `parse-order` task

`parseOrder(orderText, signal)` is call 1 of the order matching flow (ADR 0012), called by the chat for each order. The adapter sends the Owner's text wrapped in `<order>` tags. The LLM returns one line per thing to buy, `{ original, product, brand, size, quantity }`, and `ignoredPreference`, true when the Owner named a payment card or a preference for the whole order (ADR 0011). A card or a preference is never a line.

`size` and `quantity` come back as short strings that `src/core/order-matching/item.ts` parses:

- `size`: `common`, `biggest`, `smallest`, or `<amount> <ml|l|g|kg>` ("2.25 l"), parsed into `{ kind: "exact", dimension, amount }` with the amount in ml or g.
- `quantity`: `minimum`, `<n> unit` with a whole `n`, or `<amount> <g|kg>`, parsed into `{ kind: "units", count }` or `{ kind: "weight", grams }`.

Amounts are rounded to thousandths of ml or g by `roundMeasure`, the same rounding the Catalog Snapshot sizes and the Candidates use. A string the parser rejects, such as "0 kg", "0.0001 g" or "1.5 unit", fails the line schema, so the call fails like any answer that does not fit its schema. `src/core/order-matching/item-line-cases.ts` lists every accepted and rejected format; the Item tests and the line schema tests both run it.

## The `fit-products` task

`fitProducts({ item, alsoInThisLine, matches }, signal)` is call 2 of the order matching flow (ADR 0012): one call per Item, which keeps the Item's Fits among its Matches. The adapter sends one `<line>` with `<original>`, `<product>`, `<brand>`, `<also-in-this-line>` (the `product` of the other Items with the same `original`, only when there are any) and `<candidates>`, the Matches numbered from 1 as `number. name | brand | Tipo`.

The LLM returns `{ fits, closest, note, question }`: the numbers of the Matches that fit, a Note for the Owner, and, only when nothing fits, a question with up to 5 `closest` numbers. The schema cannot say how these relate, so core checks the answer against its input in `checkFitProducts` (`src/core/order-matching/match-items.ts`): every number is among the Matches, `question` is set exactly when `fits` is empty, and `closest` has at most 5 numbers and only when `fits` is empty. `matchItems` calls the port only through `checkedFitProducts`, so every adapter and every test fake goes through the same checks. A broken rule throws an error that names the task, the Item and the rule, such as `fit-products answer for Item "una cerveza" breaks a rule: no Alternatives while products fit`, and the turn ends with it.

`matchItems` in `src/core/order-matching/match-items.ts` runs the task for a set of Items, at most 10 calls at a time: for each Item it reports the step "Eligiendo productos para '<original>'", searches 30 Matches with `CatalogSearch`, runs the call, and maps the numbers back to products. It returns per Item its Matches, Fits and Note, or its question with the Alternatives in the order the LLM gave them. One call failing fails the whole set, and no further call starts. The chat calls it for each order.

## The `read-reply` task

`readReply({ items, reply }, signal)` is call 1 in follow-up mode (ADR 0012): it reads the Owner's reply to questions or to a cart. `items` holds every Item of the conversation, types in `src/core/order-matching/read-reply.ts`: an asked Item with its `original` and its question (text and Alternatives), or an Item in the cart with its `original` and the product bought. The adapter numbers them from 1 inside `<items>`, each `<item number="n" state="asked|in-cart">` with `<original>` and either `<question>` and `<alternatives>` (numbered from 1 as `number. name | brand`) or `<bought>`, then sends the reply inside `<reply>`. `takeTurn` calls it for every reply after the order, with the asked Items and the Items in the cart. The Order lists them (`replyItems` in `src/core/order-conversation/order.ts`) and reads the checked answer back (`applyReply`), so the numbering the LLM sees and the numbering read back come from one place.

The LLM returns `entries`, one per Item the reply touches: `{ item, kind: "choice", alternative }`, `{ item, kind: "lines", lines }` (Items that replace it), `{ item, kind: "drop" }` or `{ item, kind: "unanswered", question }`; plus `newLines` for things the reply adds and `ignoredPreference`. Lines come back as the strings of `parse-order` and are parsed the same way. The adapter only parses the lines. Core checks what the schema cannot in `checkReadReply` (`src/core/order-matching/read-reply.ts`): one entry at most per Item, every Item number in the list, every `alternative` among that Item's Alternatives, `choice` only for an asked Item, and `unanswered` for an Item in the cart only with a question (an ambiguous Correction, "¿Cuál coca, la zero o la normal?"). A broken rule throws an error that names the task, the Item and the rule, such as `read-reply answer for Item 2 ("coca cola zero grande") breaks a rule: a choice only for an asked Item`. It then adds `{ kind: "unanswered", question: null }` for every asked Item with no entry and returns the entries in Item order, so every asked Item has exactly one. `takeTurn` and the eval set's answer cases call the port only through `checkedReadReply`, so they and every test fake go through the same checks.

## The `plan` task

`plan({ messages, products, lastPlan }, signal)` talks a Plan over with the Owner (ADR 0013). Its input is the planning conversation (the Owner's and the planner's messages, oldest first), every product a search of this conversation returned and the last Plan shown, or null. The adapter renders `<conversation>` with one `<owner>` or `<planner>` tag per message, `<products>` with one row per product as `productId | name | brand | department | Tipo | snapshot price | sale` (`packaged, <size>`, or `by weight, Sale Step <grams> g` with the price per kg), and `<last-plan>` with its `<title>`, `<idea>` and `<lines>` (`productId | quantity | purpose | reason`), or `<last-plan>none</last-plan>`.

The LLM returns `{ kind, queries, message, plan, budget }`, one flat object, which the adapter reads as one of three outputs: `{ kind: "search", queries }`, the queries code searches in catalog words, `{ kind: "answer", message, plan | null, budget | null }`, the message to the Owner, a Plan or none, and the Owner's budget in pesos when they gave one in this conversation, or `{ kind: "confirm" }`, the Owner accepted the last Plan shown and code builds the cart from it ([ARCHITECTURE](../ARCHITECTURE.md#a-plan-end-to-end)). A Plan is `{ title, idea, lines }`: `idea` is a list of `{ heading, text }` sections and each line is `{ productId, quantity, purpose, reason }`, with whole units for a packaged product and grams for a by-weight one. A search with no queries or an answer with no message fails the schema. When code sends a Plan back over the budget, the input also has `<over-budget>` with the budget, the total and how much it is over.

Core checks the answer in `checkPlan` (`src/core/planning/plan.ts`): at most 8 queries per search and at most 60 lines; a budget, when there is one, is positive; every `productId` is among the products seen; every quantity is positive, whole units for a packaged product and whole grams for a by-weight one; a `confirm` comes only after a Plan was shown. A broken rule throws an error that names the task and the rule, such as `plan answer breaks a rule: product p9 was not returned by a search of this conversation`, and the turn ends with it. Code then merges lines with the same product ([below](#merging-lines-and-the-budget-retry)), rounds a by-weight quantity up to its Sale Step with `candidateOf`, the rule and Note of a Candidate ("Carne picada x kg se vende de a 500 g: llevo 1 kg"), and computes each line's snapshot price and the total; the LLM never gives a price. A line with no snapshot price shows none and is left out of the total.

The search loop lives in core, not in the Claude Code session, which keeps running with no tools: `planWithSearches` (`src/core/planning/plan-searches.ts`) calls the task through `checkedPlan`; while the answer is a `search`, it runs each query with `CatalogSearch` for 20 Matches, adds the products found to the products seen, each once, and calls the task again. Advice with no purchase is an answer with no Plan and keeps the conversation in `planning`; when the Owner then wants to buy, the next turn searches and answers with a Plan. A turn runs at most 3 search rounds; a fourth `search` throws `plan answer breaks a rule: a fourth search in one turn, more than 3`. Each call is the step "Armando el plan" and each round the step "Buscando '<query>', ...". The searches use scope `plan`, every in-stock product of every department, while orders keep scope `order`, which leaves out five departments ([Architecture](../ARCHITECTURE.md#ports-and-the-dependency-rule)). Every call is reported by `onCall` and every search is written to the Conversation Log as a `search-call`.

### Merging lines and the budget retry

After the checks, `checkPlan` merges the lines with the same `productId` into one, in the place of the first: the quantities are summed, and the purposes and the reasons are joined with ", ", each text once. A weekly menu that uses an onion in three dishes gets one onion line, "para el lunes, para el jueves". The merged quantity is then rounded up to the Sale Step and priced, so the total is computed on the merged lines, and the last Plan shown carries the merged lines.

`planWithinBudget` (`src/core/planning/plan-budget.ts`) wraps the search loop for every planning turn. When the answer carries a `budget` and the snapshot total of its Plan exceeds it, it runs the loop once more with the same conversation, the products seen, that Plan as `lastPlan` and `overBudget: { budget, total }`, which the adapter renders as `<over-budget>`. The retry may search again, with its own 3 rounds. The Plan it answers is shown; if it answers with no Plan or with a `confirm`, the first Plan is shown. A `confirm` answer never triggers a retry: it goes straight to the cart. When the shown Plan is still over the budget, the reply carries `overBudget`, the amount in pesos (`overBudget` in `plan.ts`), and the chat shows "Este plan se pasa de tu presupuesto por $ …" under the total. There is never a second retry. The planner repeats the budget in every answer, so a revision is checked against it too.

## Prompts

Each task's system prompt is a Markdown file in `prompts/`, named after the task: `planning/route-message.md`, `planning/plan.md`, `planning/judge-idea.md` (the judge of `pnpm plan:eval`, not an `Llm` task), `order-matching/parse-order.md`, `order-matching/fit-products.md`, and `order-matching/read-reply.md`. The adapter reads the file on each call. Prompts are LLM input, written in English; the Owner's text they receive is Spanish. `pnpm docs:check` does not check them.

## Changing a prompt

1. Edit the prompt. If the answer's shape changes, change the output type in the port and its schema in the adapter together.
2. Run `pnpm order:eval` (or `pnpm order:eval <filter>` for the cases whose id or order text contains the filter, and `--runs N` to change the 3 runs per case). It runs each case of the [eval set](#the-eval-set) with real Claude Code sessions and scores the product picked for each Item. For `route-message` and `plan`, run `pnpm plan:eval` instead ([the planning eval set](#the-planning-eval-set)).
3. Read the report: the totals, each failed case with every run's problems and what each Item came back as, stale ids, the cases that changed since the previous run, and the sessions, time and cost. Each run is saved in `.data/order-matching/eval-runs/` with the Catalog Snapshot's date, so the next run compares against it. The command exits 1 when a case not marked `expectedToFail` fails.
4. When a change fixes a case marked `expectedToFail`, the report says so; clear the mark in the eval set.

## The eval set

`evals/order-matching.json` scores the product picked per Item, not how the order was read. A case runs the flow up to the pick: call 1 (`parse-order`), the search, call 2 (`fit-products`), the size and quantity rule and the Selection Policy on Catalog Snapshot prices (the chat's Selection in `src/core/product-selection/selection.ts` with the snapshot price source), with no checkout simulation, because Branch stock and promotions change between runs. The Catalog Snapshot is not pinned: each run uses the current one and records its date.

An order case has an `id`, the `order`, an optional `expectedToFail` with the reason, an optional `ignoredPreference`, optional `notItems` (words that must not become Items) and its `items`. Each expected Item has a `product` that names it for people and is never compared, its `brand` (null, a name, or the spellings accepted), its `size` kind, its `quantity` as call 1 writes it ("minimum", "2 unit", "300 g"), and either `fits`, every in-stock `productId` that fits, with an optional `pick` (the subset that is a right pick when the size matters), or `alternatives`, the acceptable Alternatives of an Item that must ask. Each expected Item is paired with the Item that came back whose Matches, Fits and Alternatives share most of its products, then the nearest in order.

Metrics, per run and in total:

- Wrong picks nobody sees, the headline: a pick that is not right, with no Note and no question.
- Items read right: `brand`, `size` kind and `quantity` of each Item, plus the number of Items and the `notItems` per run. `product` is not compared.
- Matches recall (expected Fits among the Matches), Fits precision and Fits recall, and pick right.
- Questions asked when they should not, and not asked when they should; Alternatives among the expected ones.
- `ignoredPreference` when the case expects it.
- Stability: an Item is stable when its Fits and pick are the same in every run.
- Sessions, time and cost.

A case passes when, in every run, each expected Item gets a right pick or asks when it should. Recall, precision and stability have no threshold yet. An expected `productId` missing from the Catalog Snapshot or out of stock is reported as stale and left out of the scoring, not failed; an Item whose ids are all stale is not scored.

An answer case, under `answers`, runs only `read-reply` (`src/core/order-matching/eval-answers.ts`). It has an `id`, an optional `expectedToFail`, the fixed `items` of the conversation (an asked Item with its `original`, `question` and `alternatives` by `productId`, or an Item in the cart with its `original` and the `productId` it `bought`), the Owner's `reply`, the expected `entries` (`choice` with its Alternative number, `lines` with `product` and `brand`, `drop`, `unanswered`, which for an Item in the cart stands for an ambiguous Correction asked back; every asked Item has one, Items in the cart only when the reply touches them), the expected `newLines` and an optional `ignoredPreference`. The products are read from the Catalog Snapshot to build the input. A line matches when every word of the expected `product` is in the line's `product` and the `brand` is the same, both ignoring case and accents. An answer case passes when every run gives exactly the expected entries, `newLines` and `ignoredPreference`; the report prints how many passed and the differences of each one that failed.

Cases are labelled by hand: `pnpm order:label <words> [--brand <brand>]` lists the search's top 50 products from the Catalog Snapshot for a phrase, with `productId`, name, brand, size, price and stock. Every `productId` is checked in stock on the current snapshot when the set is written. `pnpm order:eval-set` validates the set with zod (unique ids, non-empty `productId`s with no repeats inside an Item, `pick` within `fits`, either `fits` or `alternatives`, no order equal to an example `<order>` of `prompts/`, and for answer cases one expected entry at most per Item, one for every asked Item, Item and Alternative numbers in range, and `choice` only for asked Items) and runs in `pnpm check`; it never reads the Catalog Snapshot. `pnpm order:eval` does not run in `pnpm check`, because it makes live calls and costs money.

## The planning eval set

`evals/planning.json` measures `route-message` and `plan`. Its schema, loader checks and scoring are in `src/core/planning/` (`eval-set.ts`, `eval-score.ts`, `eval-run.ts`), loaded through `loadPlanningEvalSet` of `src/compose.ts`.

- A routing case has an `id`, the Owner's `message`, the expected `topic` (`order`, `plan` or `off-topic`) and an optional `expectedToFail`. A run calls `routeMessage` once and passes when the Topic is the expected one.
- A plan case has an `id`, the Owner's first `message`, `covers` (the cases of the meal-planner spec it stands for: `recipe`, `event`, `weekly-menu`, `gift`, `advice`, `constraints`, `idea-in-cart`; routing cases with Topic `off-topic` cover `off-topic`), `plan` (whether a Plan must be shown) and optional `expectedToFail`, `budget`, `quantities`, `forbiddenProductIds`, `forbiddenWords`, `allowedWords` and `idea`. A run sends the message as the whole planning conversation through `planWithinBudget`, the chat's search loop and budget retry, and scores the first answer shown after its search rounds.

Code scores each plan run (`scorePlanRun`):

- A Plan is shown when `plan` is true, and none when it is false (advice with no purchase).
- Every line is in stock in the Catalog Snapshot.
- The total is within `budget`.
- Each range of `quantities` sums the lines whose `productId` is in its `productIds`, in its `unit`: `g` (grams of a by-weight product, or units times the size of a packaged one sold by weight), `ml` (units times the size of a packaged one sold by volume) or `unit` (units of a packaged product); the sum is within `min` and `max`, and a line that cannot be measured in that unit is a problem.
- No line is a product of `forbiddenProductIds`, and no line's name has a word of `forbiddenWords` (a whole word or phrase, ignoring case and accents) unless it also has a word of `allowedWords` ("fideos" is forbidden for "sin TACC", "fideos sin TACC" is allowed).
- One line per product: the Plan the planner answered has no `productId` twice, before code merges the lines.
- The Idea has at least `idea.min` sections, counting only those whose heading has a word of `idea.headings` when given ("lunes" ... "viernes" for a weekly menu, "pasos" for a recipe).

A case passes when every run gives no error and keeps every rule. An LLM judge, the `judge-idea` session (`prompts/planning/judge-idea.md`, `claude-sonnet-5-5` at its default effort, `createClaudeCodeIdeaJudge`), reads the request, the message and the Plan of every plan run that answered and returns `{ sensible, reason }` by a fixed rubric. Its judgment is reported apart, as the Ideas judged sensible and the reasons of those that are not, and never fails a run or the command.

`pnpm plan:eval [filter...] [--runs N]` runs the cases whose id or message contains a filter, 3 times each by default, with real Claude Code sessions. The report gives the cases passed, the errors, the Ideas judged sensible, stale `productId`s (missing or out of stock in the current Catalog Snapshot), a table with each case's sessions, time and cost per run and its cost, every failed run with its problems and its Plan, and the totals. Each run is saved in `.data/planning/eval-runs/`. The command exits 1 when a case not marked `expectedToFail` fails.

Cases are labelled by hand with `pnpm order:label <words>`, which lists the `productId`s a range or a forbidden product names. `pnpm plan:eval-set` validates the set with zod (unique ids across both kinds, no message equal to an example `<message>` or first `<owner>` message of `prompts/`, a range's `min` at most its `max`, no Plan rule in a case that expects no Plan, and every case of the spec covered) and runs in `pnpm check`; it never reads the Catalog Snapshot. `pnpm plan:eval` does not run in `pnpm check`, because it makes live calls and costs money.
